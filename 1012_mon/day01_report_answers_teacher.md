## 2교시 · ping

### 문제 2-1 · 결과 화면 읽기

- **보냄 · 받음 · 손실 · 평균:** `4 · 3 · 25% · 47ms` (예시 화면이라 모두 같은 값)
- **손실 % 는 어떻게 계산했나요?**
  - 모범 답: 4개를 보내 3개가 돌아왔으니 1개가 사라졌다. 1 ÷ 4 = 25%.
  - 핵심 낱말: **(보낸 수 − 받은 수) ÷ 보낸 수**

### 문제 2-2 · 구글 DNS 서버에 `ping` 열 번 보내기

- **평균 · TTL · 받음 · 손실:** 예) `평균 34ms · TTL 115 · 받음 10 · 손실 0%`
  - 확인할 것: 받음이 **10 개 중** 몇 개인지 적었는가(`-n 10` 을 했는가). 평균은 `시간=` 한 줄이 아니라 맨 아래 `평균 =` 값인가.

### 문제 2-3 · 이름으로 `ping` 보내기

- **`google.com` 의 IP 주소:** 예) `142.250.196.110` — 사람마다 다를 수 있음
  - 확인할 것: 결과 **첫 줄 대괄호 `[ ]` 안**의 숫자인가.
- **이름만 입력했는데 IP 가 나온 이유는?**
  - 모범 답: 컴퓨터는 이름으로 통신하지 못한다. `ping` 이 먼저 DNS 에 물어 이름을 IP 로 바꾸고, 그 IP 로 보냈다.
  - 핵심 낱말: **DNS · 이름 → IP**

### 문제 2-4 · 두 가지 실패를 구별하기

- **두 실패 문구:** `호스트를 찾을 수 없습니다` · `요청 시간이 만료되었습니다`
- **각각 어디에서 멈췄나요?**
  - 모범 답: 첫째는 이름을 IP 로 바꾸지 못해 **보내기 전에** 멈췄다. 둘째는 IP 로 보냈지만 **답이 돌아오지 않았다**.
  - 핵심 낱말: **이름 변환 실패 / 응답 없음**

### 찾아본 것

- **TTL 의 뜻과 라우터를 지날 때 바뀌는 방식:**
  - 모범 답: TTL 은 패킷이 거쳐 갈 수 있는 남은 횟수다. 라우터(공유기)를 하나 지날 때마다 1씩 줄어든다.
  - 핵심 낱말: **남은 횟수 · 1씩 줄어든다**

### 이 교시에 새로 안 것

- 자유. 「`ping` 결과에서 평균 · 손실 · TTL 을 읽는 법」, 「이름 실패와 응답 없음은 다르다」 정도면 충분합니다.

## 3교시 · IP 와 MAC

### 문제 3-1 · 결과 화면 읽기

- **IPv4 · MAC · 기본 게이트웨이:** `192.168.0.15 · A4-B1-C2-D3-E4-F5 · 192.168.0.1` (예시 화면이라 모두 같은 값)
  - 확인할 것: MAC 은 `-` 로 나뉜 6 덩어리, IP 는 점으로 나뉜 4 덩어리.

### 문제 3-2 · 내 IP 주소 · 게이트웨이 · MAC 주소 찾기

- **장치 이름 · IPv4 · 게이트웨이 · MAC:** 예) `이더넷 2 · 192.168.10.25 · 192.168.1.1 · 3C-7C-3F-12-AB-CD`
  - 확인할 것: 네 값이 **모두 같은 장치** 아래에서 나왔는가. 게이트웨이 칸이 빈 장치의 값을 적지 않았는가.

### 문제 3-3 · 게이트웨이까지 `ping`

- **게이트웨이 평균 · `8.8.8.8` 평균:** 예) `1ms · 34ms`
  - 확인할 것: 게이트웨이 쪽이 훨씬 작다. 예시 주소 `192.168.0.1` 이 아니라 **내 게이트웨이**로 보냈는가.
- **게이트웨이까지가 더 짧은 이유는?**
  - 모범 답: 게이트웨이(공유기)는 같은 건물 안에 있고, `8.8.8.8` 은 인터넷 건너편에 있다. 가깝고 거치는 장비가 적을수록 왕복 시간이 짧다.
  - 핵심 낱말: **가깝다 · 거치는 장비가 적다**

### 문제 3-4 · ARP 캐시 보기 — `arp -a`

- **게이트웨이 줄의 MAC · 유형:** 예) `a8-5e-45-01-2b-3c · 동적`
  - 확인할 것: `인터넷 주소` 가 **내 기본 게이트웨이**인 줄을 골랐는가. 유형은 `동적`.
- **🔍 ARP 는 무엇을 알아내려고 쓰나요?**
  - 모범 답: 같은 망에서 「이 IP 의 MAC 이 뭐예요?」 하고 묻는 방법이다. 내 PC 는 게이트웨이 `192.168.1.1` 에 보내려고 그 MAC 주소를 ARP 로 물어 알아냈고, 그 답이 ARP 캐시에 남았다.
  - 핵심 낱말: **IP 로 MAC 을 알아낸다**

### 이 교시에 새로 안 것

- 자유. 「IP 는 3층 주소, MAC 은 2층 주소」, 「같은 망 밖으로 나갈 때는 게이트웨이를 거친다」 정도면 충분합니다.

## 4교시 · 포트

### 문제 4-1 · 직접 실행해 보기

- **출력 두 줄:** `HTTPS` · `모름`
- **`3389` 는 사전에 없는데도 에러 없이 둘째 줄이 나온 이유는?**
  - 모범 답: `.get(3389, "모름")` 은 키가 없으면 두 번째 값 `"모름"` 을 리턴한다. 대괄호 `PORTS[3389]` 로 꺼냈다면 `KeyError` 가 났다.
  - 핵심 낱말: **`.get` 의 두 번째 값**

### 문제 4-2 · 지금의 연결과 그 프로그램 — `netstat -ano`

- **외부 포트 → 서비스 이름 · PID → 프로그램 이름:** 예) `443 → HTTPS` · `8124 → chrome.exe` (또는 `msedge.exe`)
  - 확인할 것: `ESTABLISHED` 줄의 **외부 주소** 쪽 포트인가(로컬 주소의 큰 숫자 아님). PID 는 **같은 줄** 맨 끝 숫자인가.

### 문제 4-3 · 내 PC 의 LISTENING 포트 찾기

- **4.1 표에 있는 LISTENING 포트 → 서비스:** 예) `135 → RPC` · `445 → SMB`
- **🔍 LISTENING 과 ESTABLISHED 는 무엇이 다른가요?**
  - 모범 답: LISTENING 은 내 PC 가 연결 요청을 **기다리며 열어 둔** 상태(4-3 의 445)이고, ESTABLISHED 는 상대와 **연결되어 대화 중**인 상태(4-2 의 443 줄)다.
  - 핵심 낱말: **기다림 / 대화 중**

### 문제 4-4 · 증상으로 층 좁히기

- **의심되는 층:** ① 7층 DNS ② 1~3층(선 · Wi-Fi · 공유기) ③ 4층 이상(그 서버의 포트 · 서비스)
- **판단한 근거는?**
  - 모범 답:
    - ① 숫자 주소 `ping` 은 되니 3층까지는 정상이고, 이름을 IP 로 바꾸는 DNS 만 안 된다.
    - ② 바로 옆 게이트웨이부터 답이 없으니 우리 망 안(선 · Wi-Fi · 공유기)이 문제다.
    - ③ `ping` 이 다 되니 3층까지는 정상이고, 그 사이트의 포트나 서비스가 문제다.
  - 핵심 낱말: **아래 층부터 확인 · 처음 안 되는 층이 원인**

### 찾아본 것

- **3389 의 위험 · 445 로 퍼진 랜섬웨어:**
  - 모범 답: 3389 는 원격 데스크톱(RDP)이라, 인터넷에 열려 있으면 바깥에서 내 PC 로 접속을 시도하는 공격 대상이 된다. 445(SMB, 파일 공유)로는 2017 년 워너크라이(WannaCry) 랜섬웨어가 퍼졌다.
  - 핵심 낱말: **원격 접속 공격 대상 · 워너크라이**

### 이 교시에 새로 안 것

- 자유. 「포트 번호로 서비스를 알 수 있다」, 「PID 로 연결을 연 프로그램을 찾는다」 정도면 충분합니다.

## 5교시 · TCP

### 문제 5-1 · 직접 실행해 보기

- **출력 세 줄:** `True` · `False` · `443`
- **탐지 코드에서 플래그를 `==` 로 검사하면?**
  - 모범 답: `==` 는 리스트 **전체**를 글자 `"ACK"` 와 비교하므로 늘 `False` 다(둘째 줄). 에러가 나지 않아서, 탐지 규칙이 **아무것도 못 잡는데도 모르고 지나간다**. 그래서 `in` 으로 검사한다.
  - 핵심 낱말: **에러 없이 늘 False · `in` 으로**

### 문제 5-2 · TCP 일까 UDP 일까

- **① ~ ⑤:** ① TCP ② UDP ③ TCP ④ UDP ⑤ ICMP(둘 다 아님)
- **① 사진 파일 보내기가 TCP 인 이유는?**
  - 모범 답: 파일은 한 조각이라도 빠지면 깨진다. TCP 는 받았는지 확인하고 안 왔으면 다시 보내서 빠짐없이 전한다.
  - 핵심 낱말: **확인 · 다시 보낸다**

### 문제 5-3 · 세 번의 순서 맞히기

- **순서와 방향:** (나) `[SYN]` 내 PC → 서버 · (다) `[SYN, ACK]` 서버 → 내 PC · (가) `[ACK]` 내 PC → 서버
- **🔍 맺을 때는 세 번인데, 끝낼 때는 왜 네 번인가요?**
  - 모범 답: 맺을 때는 서버의 「알았다(ACK)」와 「나도 연결하자(SYN)」를 한 번에 보낼 수 있다. 끝낼 때는 서버에 아직 보낼 데이터가 남아 있을 수 있어서, 「알았다」를 먼저 보내고 「나도 다 보냈다(FIN)」는 **나중에 따로** 보낸다.
  - 핵심 낱말: **보낼 데이터가 남아 있어 따로 보낸다**

### 문제 5-4 · 같은 서버로 간 두 연결은 무엇이 다른가

- **같은 것 · 다른 것:** 같은 것 — 외부 주소(서버 IP · 포트 443)와 내 IP. 다른 것 — 로컬 주소 끝의 포트(예: `51234` · `51240`).
- **두 연결을 무엇으로 구별하나요?**
  - 모범 답: 연결 하나는 출발지 IP · 출발지 포트 · 목적지 IP · 목적지 포트 네 값으로 정해진다. 나머지가 같으니 내 PC 가 연결마다 다르게 고른 **임시 포트**로 구별한다.
  - 핵심 낱말: **임시 포트(출발지 포트)**

### 이 교시에 새로 안 것

- 자유. 「TCP 는 3-way 로 연결을 맺는다」, 「연결은 네 값으로 구별된다」 정도면 충분합니다.

## 6교시 · Wireshark

### 문제 6-1 · Wireshark 실행하기

- **고른 인터페이스 이름:** `이더넷 2` (노트북은 Wi-Fi 이름)
  - 확인할 것: 오른쪽 그래프가 움직이는 인터페이스인가.

### 문제 6-2 · 캡처한 통신의 방향 읽기

- **`Packets` · Protocol 이름 세 개:** 예) `Packets: 1532` · `TCP · UDP · DNS` (또는 `TLSv1.3`)
  - 확인할 것: 숫자가 0 이 아닌가.
- **어느 줄이 요청인가요? 이유는?**
  - 모범 답: `숫자 → 443` 줄이 요청이다. 내 PC 가 임시 포트(숫자)에서 서버의 443 으로 보냈기 때문이다. `443 → 숫자` 는 서버가 돌려보낸 응답이다.
  - 핵심 낱말: **임시 포트 → 443 = 요청**

### 문제 6-3 · 패킷 하나를 층별로 펼치기

- **MAC · IP · TTL · 포트 · Flags:** 예) `3C-7C-3F-12-AB-CD · 192.168.10.25 / 142.250.196.110 · 128 · 51234 / 443 · ACK`
  - 확인할 것: 포트를 IP 줄이 아니라 `Transmission Control Protocol` 안에서 찾았는가. Flags 는 괄호 안 이름(`ACK`, `PSH, ACK` 등).
- **내 PC 가 보낸 것인가요, 받은 것인가요?**
  - 모범 답: Source IP 가 3-2 에서 찾은 **내 IPv4 주소와 같으므로** 내 PC 가 보낸 패킷이다. (Destination 이 내 IP 면 받은 패킷)
  - 핵심 낱말: **Source IP = 내 IP**

### 문제 6-4 · 필터 결과와 뜻 비교하기

- **`Packets` · `dns` · `udp` · `tcp.port == 443` 의 `Displayed`:** 예) `1532 · 24 · 31 · 611`
  - 확인할 것: 세 숫자 모두 `Packets` 보다 작다. `dns` 와 `udp` 가 비슷하다(UDP 대부분이 DNS).
- **`Packets` 는 그대로인데 `Displayed` 만 바뀌는 이유는?**
  - 모범 답: 표시 필터는 패킷을 지우지 않고, 조건에 맞는 줄만 **화면에 보여 준다**. 그래서 잡은 전체 수(`Packets`)는 그대로이고 보이는 수(`Displayed`)만 바뀐다.
  - 핵심 낱말: **지우지 않고 가린다**

### 이 교시에 새로 안 것

- 자유. 「패킷 하나에 층마다 헤더가 붙어 있다」, 「표시 필터로 원하는 것만 본다」 정도면 충분합니다.

## 7교시 · 패킷 분석

### 문제 7-1 · 내 HTTP 연결 하나만 잡기

- **세 줄 Info 의 신호 순서:** `[SYN] → [SYN, ACK] → [ACK]`
  - 확인할 것: 순서가 이대로인가. 내 `curl` 연결의 세 줄인가(출발지 포트가 같은 세 줄).

### 문제 7-2 · HTTP 요청과 연결 종료 찾기

- **요청 줄의 Info · FIN 줄 수:** `GET /?q=network_day1 HTTP/1.1 · 2 줄`
  - 확인할 것: FIN 은 Info 에 `[FIN, ACK]` 로 보인다. RST 가 보이는 등 1 줄이어도, 이유를 적었으면 인정.
- **🔍 HTTPS 로 보냈다면 어떻게 보였을까요?**
  - 모범 답: HTTPS 는 내용을 **암호화**해서 보내므로, Wireshark 에서 `TLSv1.3` 같은 줄만 보이고 `GET /?q=network_day1` 같은 요청 내용과 검색어는 보이지 않았을 것이다.
  - 핵심 낱말: **암호화되어 안 보인다**

### 문제 7-3 · 보고서 완성하고 올리기

- **깃허브 `network_zt` 폴더에 보고서가 보이나요:** `예`
  - 확인할 것: 깃허브에서 보고서를 열었을 때 빈칸이 없다. `.env` 가 커밋되지 않았다(깃허브 저장소 맨 위에 `.env` 가 없다).

### 이 교시에 새로 안 것

- 자유. 「암호화하지 않은 HTTP 는 내용이 그대로 보인다」 정도면 충분합니다.

## 최종 분석

### 1. 연결이 열리는 순간 — 3-way handshake

- **Source → Destination 과 Info:** 예)
  - ① `192.168.10.25 → 93.184.215.14 · [SYN]`
  - ② `93.184.215.14 → 192.168.10.25 · [SYN, ACK]`
  - ③ `192.168.10.25 → 93.184.215.14 · [ACK]`
  - 확인할 것: ① ③ 은 내 PC 가 보낸 것, ② 는 서버가 보낸 것. 서버 IP 는 실행할 때마다 다를 수 있음.
- **세 줄이 오간 뒤 어떤 상태가 되나요?**
  - 모범 답: 둘 사이에 연결이 맺어져 데이터를 주고받을 수 있게 된다. `netstat` 으로 보면 `ESTABLISHED` 상태다.
  - 핵심 낱말: **연결됨 · ESTABLISHED**

### 2. 패킷 하나를 열어 본 값 — 6-3

- **IP (3층) · TTL · 포트 (4층):** 6-3 에서 적은 값을 층별로 옮기면 됩니다. IP 와 TTL 은 3층, 포트는 4층으로 나누었는지 봅니다.
- **목적지 포트로 서비스를 알 수 있나요?**
  - 모범 답: 알 수 있다. 목적지 포트가 443 이면 4.1 표에 따라 HTTPS(암호화된 웹)로 가는 패킷이다.
  - 핵심 낱말: **443 → HTTPS**

### 3. HTTP 요청 — 7-2

- **그대로 보인 내용:** `GET /?q=network_day1` — 내가 보낸 검색어 `network_day1`
- **보안에서 문제가 되는 이유는?**
  - 모범 답: 암호화하지 않아서, 중간에서 패킷을 잡은 사람도 검색어 · 비밀번호 같은 내용을 그대로 읽을 수 있다. 그래서 웹은 HTTPS 를 써야 한다.
  - 핵심 낱말: **누구나 읽을 수 있다 · HTTPS**
