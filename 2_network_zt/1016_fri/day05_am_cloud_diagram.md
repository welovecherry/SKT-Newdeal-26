> - 이 교시에서 하는 일: 서비스 형태를 구분하고, 방화벽 로그에 없는 접속을 찾습니다.

### 왜 필요한가

- 서버와 업무 도구가 클라우드로 옮겨 가면서, 어디까지 업체가 관리하고 어디부터 내가 관리하는지가 서비스마다 달라졌습니다.
- 내가 관리하는 범위가 좁을수록 걸 수 있는 보안 설정도 줄어듭니다. 그래서 서비스를 만나면 **형태부터 구분**합니다.
- 직원이 집에서 SaaS 에 바로 접속하면 그 접속은 회사 방화벽을 지나지 않습니다. 보안팀이 볼 수 있는 것은 그 서비스가 남겨 주는 로그뿐입니다.

### 2.1 클라우드 서비스의 세 형태 — 어디까지 남이 관리하나

- **클라우드**(cloud · 클라우드)
  - 내 건물이 아니라 업체의 서버를 인터넷으로 빌려 쓰는 방식
- **IaaS**(Infrastructure as a Service · 아이아스)
  - 서버와 저장소, 네트워크만 빌린다
  - 운영체제 설치 · 패치 · 보안 설정은 **내가 한다**
- **PaaS**(Platform as a Service · 파스)
  - 운영체제와 실행 환경까지 업체가 관리한다
  - **코드와 데이터**만 내가 맡는다
- **SaaS**(Software as a Service · 사스)
  - 완성된 서비스를 계정만 받아 쓴다
  - **계정 · 권한 · 데이터**만 내가 맡는다

| 형태 | 내가 맡는 것 | 방화벽 규칙을 직접 걸 수 있나 |
|---|---|---|
| IaaS | 운영체제 · 보안 설정 · 코드 · 데이터 | 걸 수 있다 |
| PaaS | 코드 · 데이터 | 일부만 걸 수 있다 |
| SaaS | 계정 · 권한 · 데이터 | 걸 자리가 없다 |

- 위에서 아래로 갈수록 내가 쓸 수 있는 통제 수단이 줄고, SaaS 에서는 **계정과 권한**이 남습니다.

**실제 서비스로 보면**

| 형태 | 대표 서비스 | 회사가 하는 일의 예 |
|---|---|---|
| IaaS | **AWS EC2** · Google Compute Engine · Azure Virtual Machines | EC2 에서 가상 서버를 만들고, 운영체제(Linux · Windows)를 고르고, 웹 서버 프로그램을 설치한다. **보안 그룹**(클라우드의 방화벽)에서 443 만 열어 둔다 |
| PaaS | **Vercel** · Heroku · Azure App Service | 코드를 Vercel 에 올리면 서버 · 운영체제 관리 없이 웹사이트가 배포된다. 회사는 코드 · 환경 설정 · 데이터를 관리한다 |
| SaaS | **Google Docs**(Google Workspace) · Microsoft 365 · Slack | 직원 계정을 만들고 초대한다. 프로그램을 설치하거나 서버를 두지 않는다. 회사는 계정과 권한 · 공유 범위를 관리한다 |

- 한 회사가 **세 가지를 함께 쓰는 경우**가 흔합니다.
  - 예: 회사 소개 웹사이트는 <mark>Vercel</mark>(PaaS), 사내 DB 서버는 <mark>EC2</mark>(IaaS), 업무 문서는 <mark>Google Docs</mark>(SaaS)
  - 고객사에서 사고가 나면 **어느 서비스에서 났는지**를 가장 먼저 보고합니다.

### ✍️ 문제 2-1 · 서비스 형태 네 개 가르고 먼저 볼 기록 정하기

**📍 이런 상황이 있습니다**

- 중소기업 A사는 회사 소개 웹사이트는 <mark>Vercel</mark>, 사내 서버는 <mark>EC2</mark>, 업무 문서는 <mark>Google Docs</mark> 에 나눠 쓰고 있습니다.
- 어느 날 「서비스에 이상한 접속이 있다」는 신고가 들어옵니다. 보안 담당이 가장 먼저 확인할 것은 어느 서비스에서 일어난 일인지입니다.
  - EC2 서버라면 회사가 직접 관리하므로 <mark>서버 로그와 방화벽 로그</mark>를 봅니다.
  - Google Docs 라면 서비스의 <mark>로그인 기록</mark>을 봅니다.
- 이 문제는 서비스 네 개를 보고, 어디까지가 회사 일이고 먼저 볼 기록이 무엇인지 구분하는 연습입니다.

**🎯 할 일**

1. 아래 <mark>서비스 A · B · C · D</mark> 네 개를 읽습니다.

3. 서비스 C 에서 <mark>회사가 직접 맡는 것</mark>을 찾습니다.
4. 서비스 A 와 C 에서 사고가 났을 때 <mark>먼저 볼 기록</mark>을 고릅니다.


**서비스 네 개**

- **서비스 A:** 클라우드에서 빈 가상 서버를 빌려, 운영체제 설치와 보안 설정까지 직접 해서 웹 서버로 씁니다. (예: **AWS EC2** 에서 만든 서버)
- **서비스 B:** 코드만 올리면 서버 · 운영체제 관리는 업체가 해 주고, 회사는 코드와 데이터만 관리합니다. (예: **Vercel** 에 올린 회사 소개 웹사이트)
- **서비스 C:** 메일 · 문서 협업 도구를 계정만 받아 씁니다. 회사는 직원 계정과 접근 권한만 관리합니다. (예: **Google Docs** · **Slack**)
- **서비스 D:** 운영체제와 실행 환경은 업체가 관리합니다. 회사는 직접 만든 프로그램과 데이터를 올리고, **직원 계정과 접근 권한도 회사가 정합니다.** (예: **Azure App Service** 에 올린 사내 업무 프로그램)

**순서**

1. 위 네 서비스를 읽고, 먼저 서비스마다 운영체제 설치와 관리를 회사가 직접 하는지 확인합니다.
   - 하면 → IaaS
   - 안 하고 코드와 데이터를 올리면 → PaaS
   - 안 하고 계정과 데이터만 다루면 → SaaS
2. **[보고서]** `day05_am_report.md` 의 `## 2교시` › `### 문제 2-1` 아래를 채웁니다.
   - (가-1) 서비스 A · B · C · D 는 각각 IaaS · PaaS · SaaS 중 무엇인가요?
   - (가-2) 서비스 C 에서 회사가 직접 맡는 것 세 가지를 적어 주세요.
   - (나) 🔍 서비스 C 에는 방화벽 규칙을 직접 걸 수 없습니다. 그러면 회사에 남는 통제 수단은 무엇일까요?
   - (다) 서비스 A 와 서비스 C 에서 사고가 났을 때, 회사가 먼저 볼 기록은 각각 무엇인가요?

**💡 힌트**

1. 서비스 D 는 계정을 관리하지만, 운영체제와 실행 환경은 업체가 관리합니다. 이 점이 B 와 어떻게 같은지 살펴봅니다.
2. SaaS 는 회사가 코드를 올리지 않습니다. 코드를 올렸다면 SaaS 가 아닙니다.

### 2.2 회사 방화벽을 지나지 않는 접속

- **예전 접속 경로**
  - 사내 PC → 사내망 → 회사 방화벽 → 인터넷
  - 모든 접속이 방화벽 한 곳을 지나므로 거기서 기록하고 막을 수 있었다
- **재택근무 뒤의 접속 경로**
  - 집 PC → 인터넷 → SaaS 서비스
  - 회사 망 · 회사 방화벽을 거치지 않는다. 방화벽 로그에는 이 접속이 **남지 않는다**
- **가시성**(visibility · 비저빌리티)
  - 무슨 일이 일어나는지 보안팀이 볼 수 있는 정도
  - 접속이 회사 방화벽을 지나지 않으면 가시성이 떨어진다. 이때 볼 수 있는 곳은 **그 서비스의 로그인 기록**뿐이다
- **현실에서 마주치는 곳**
  - 직원이 집에서 <mark>Google Docs</mark> · <mark>Slack</mark> 에 로그인하면 회사 방화벽을 지나지 않는다
  - 그래서 보안팀은 방화벽 로그가 아니라 **서비스의 접속 기록**(Google Workspace 의 로그인 기록 등)을 본다
  - 퇴사자 계정이 새벽에 낯선 IP 로 로그인하면 계정 도용을 의심하는 전형적인 경우이다

### ✍️ 문제 2-2 · 방화벽 로그에 없는 접속 찾고 조치 보고 평가하기

**📍 이런 상황이 있습니다**

- 쇼핑몰 B사에서 퇴사 예정인 직원 lee 의 계정이 협업 서비스에 <mark>새벽 3시</mark>에 로그인된 기록이 발견됩니다.
- 보안 담당이 회사 방화벽 로그를 열어 보니 그 시각에 아무 기록이 없습니다. 경영진이 「방화벽에 안 남았으니 괜찮은 것 아닌가요?」라고 묻습니다.
  - 집이나 카페에서 서비스에 직접 접속하면 <mark>회사 방화벽을 지나지 않아</mark> 기록이 남지 않습니다.
- 담당자는 비밀번호를 바꾸고 「이제 안전합니다」라고 보고했습니다. 이 보고에서 <mark>빠진 것이 무엇인지</mark> 찾아내는 문제입니다.
- 현업에서는 SIEM 같은 도구로 수만 줄에서 이런 대조를 합니다. 오늘은 **6줄로 줄인 로그**로, 직원이 SaaS 에 직접 접속하는 경우만 연습합니다.

**🎯 할 일**

1. 아래 두 로그를 <mark>시각이 같은 줄</mark>끼리 맞춰, 방화벽 로그에 <mark>짝이 없는 로그인</mark>을 찾고 그중 <mark>가장 수상한 하나</mark>를 고릅니다.
2. 아래 <mark>담당자 조치 보고</mark>에서 <mark>확인된 것</mark>과 <mark>확인하지 못한 것</mark>을 나눕니다.
3. 고객에게 보낼 <mark>한 문장</mark>을 씁니다.


**이 문제에 나오는 말**

- **공인 IP**(public IP · 퍼블릭 아이피)
  - 인터넷에서 보이는 주소. 사내 PC 는 모두 회사 공인 IP `203.0.113.10` 으로 나가서 SaaS 에는 이 주소로 보인다(10/13 NAT)

**SaaS 로그인 기록** (오늘 하루, 협업 도구 서비스가 남긴 기록)

| 번호 | 시각 | 사용자 | 접속한 IP |
|---|---|---|---|
| ① | 03:12 | lee | 192.0.2.88 |
| ② | 09:02 | kim | 203.0.113.10 |
| ③ | 09:15 | lee | 203.0.113.10 |
| ④ | 09:40 | park | 198.51.100.7 |
| ⑤ | 11:30 | kim | 203.0.113.10 |
| ⑥ | 14:05 | choi | 198.51.100.44 |

**회사 방화벽 로그** (오늘 하루, SaaS 로 나간 443 포트 연결만)

| 시각 | 사내 PC | 도착지 | 처리 |
|---|---|---|---|
| 09:02 | PC-kim | SaaS 서버 | 허용 |
| 09:15 | PC-lee | SaaS 서버 | 허용 |
| 11:30 | PC-kim | SaaS 서버 | 허용 |

**담당자 조치 보고 (예시)**

- **조치:** ①번 로그인(lee, 03:12)을 발견하고 lee 계정의 <mark>비밀번호를 바꿨다</mark>. (오전 10:00)
- **보고:** 「비밀번호를 바꿨으니 <mark>이제 안전합니다</mark>. 03:12 접속에서 <mark>외부인이 열람한 자료는 없습니다</mark>.」
- **보안팀이 볼 수 있는 것:** 서비스의 접근 기록(열람 · 다운로드). 시각 · 계정 · 접속 IP 가 남는다.

**순서**

1. 두 표를 <mark>시각</mark>으로 맞춰 봅니다.
   - 방화벽 로그에 같은 시각의 줄이 있으면 → <mark>사내에서 접속</mark>한 것입니다
   - 같은 시각의 줄이 없으면 → <mark>방화벽을 지나지 않은 접속</mark>입니다 (①번 접속은 방화벽 로그만으로는 알 수 없습니다)
2. 조치 보고 문장을 둘로 나눕니다.

# <mark style="display:block; background:#c8e6c9; color:#1a1a1a; padding:6px 12px; border-radius:4px">3교시 (11:00–11:50) · 망 구성도 읽고 고치기 · DMZ</mark>

> 📨 **오늘 들어온 일**
> 고객사 보안 담당이 보낸 메시지: 「고객이 구성도를 보냈습니다. 웹 서버가 어디에 있어야 안전한가요? 한 줄로 알려 주세요.」
> - 이 교시에서 하는 일: 구성도를 읽고 DMZ 인지 판정한 뒤, 경보 로그와 함께 읽어 잘못 열린 길을 찾아 ASCII 로 고쳐 그립니다.
> - 끝나면 쓰는 것: **보고서 한 줄**(고객에게 보낼 답 한 문장)

### 왜 필요한가

- 고객사 환경을 처음 받으면 가장 먼저 구성도를 봅니다. 어느 서버가 인터넷에 열려 있고 어느 서버가 안쪽에 있는지가 구성도에 나옵니다.
- 공개 서버(웹 서버)가 내부망 안에 있는지, 따로 떼어 둔 구역에 있는지에 따라 사고 때 피해 범위가 달라집니다.

### 3.1 구성도를 읽는 순서

- **구성도**(diagram · 다이어그램)
  - 장비와 그 사이의 연결을 그린 그림
- **구역**(zone · 존)
  - 방화벽이 네트워크를 나눈 칸. 오늘은 `outside`(인터넷 쪽) · `DMZ` · `inside`(내부망) 세 구역을 쓴다
- **DMZ**(demilitarized zone · 디엠지)
  - 밖에 공개하는 서버만 따로 둔 중간 구역
  - 웹 서버가 뚫려도 내부 서버로 가려면 방화벽을 한 번 더 지나야 한다

### 도식 읽는 법 — 오늘 쓰는 기호

구성도는 글자와 선으로 그립니다. 문제를 풀기 전에 기호가 무엇을 뜻하는지 먼저 봅니다.

| 모양 | 뜻 |
|---|---|
| `INTERNET` | 인터넷. 도식의 바깥쪽입니다 |
| `FW` | **방화벽**(firewall). 지나가는 통신을 허용하거나 차단하는 장비입니다. 방화벽이 여러 대면 `FW1` · `FW2` 처럼 번호를 붙입니다 |
| `INSIDE` | 내부망. 직원 PC · 내부 서버가 있는 안쪽 구역입니다 |
| `( WEB )` | **괄호 안은 그 구역에 있는 서버 이름**입니다. `( WEB · DB )` 처럼 `·` 로 이으면 서버가 여러 대입니다 |
| `WEB` | 웹 서버. 고객이 접속하는 웹사이트를 돌리는 서버입니다 |
| `DB` | 데이터베이스 서버. 고객 정보 같은 자료를 저장하는 서버입니다 |
| `────` | 연결선. 통신이 오가는 길입니다 |
| `┬` · `│` · `└` | 한 선이 둘로 **갈라지는** 모양입니다. `┬` 는 갈라지는 곳, `└` 는 마지막 가지입니다 |
| `: WEB (443 open)` | 3-2 에서 쓰는 표기입니다. 콜론 뒤는 서버, 괄호는 인터넷에 **열어 둔 포트**입니다 |

**읽는 순서: 왼쪽에서 오른쪽으로, 선을 따라갑니다.**

```
INTERNET ──── FW ──── INSIDE ( PC · FILE )
```

1. 왼쪽 `INTERNET` 에서 출발합니다.
2. 선을 따라가면 `FW`(방화벽)를 지납니다.
3. 그 뒤 `INSIDE`(내부망) 구역이 나옵니다.
4. 괄호 안에 `PC`(직원 PC)와 `FILE`(파일 서버)가 있습니다.
5. 읽은 결과: 「인터넷에서 오는 통신은 방화벽을 지나 내부망으로 들어가고, 내부망 안에 직원 PC 와 파일 서버가 있다. 공개 서버는 없다.」

**갈라지는 선은 위에서 아래로 읽습니다.**

```
INTERNET ──── FW ──┬── DMZ    ( MAIL )
                   └── INSIDE ( PC )
```

`FW` 에서 선이 두 갈래로 나뉩니다. 위쪽은 `DMZ` 구역(`MAIL` 메일 서버), 아래쪽은 `INSIDE` 구역(`PC`)입니다. 읽은 결과: 「방화벽 한 대가 DMZ 와 내부망으로 길을 나누고, 메일 서버는 DMZ, 직원 PC 는 내부망에 있다.」

- 도식 안의 이름은 **영어와 숫자**로 씁니다. 한글은 글자 폭이 달라서 선이 어긋납니다.

- 공개 서버가 내부 서버와 **같은 구역**에 그려져 있으면 DMZ 가 없는 구성입니다. 방화벽 개수만 보고 판단하지 않습니다.

**현실에서 마주치는 곳**

- 회사 홈페이지 서버 · 메일 서버처럼 <mark>인터넷에서 접속해야 하는 서버</mark>는 DMZ 에 두고, 직원 DB · 파일 서버는 <mark>내부망</mark>에 둡니다.
- 클라우드에서도 같은 원칙을 씁니다. 예: **EC2** 에 만든 웹 서버는 보안 그룹으로 443 만 열고, DB 서버는 인터넷에서 접근할 수 없는 곳에 둡니다.

- 현실에서도 구조가 같습니다. 사내 방화벽 장비의 규칙표와 **AWS EC2 의 보안 그룹**은 모두 <mark>출발 · 포트 · 허용</mark> 칸으로 씁니다. 오늘 코드는 이 구조를 가장 단순하게 옮긴 것입니다.

#### 🐍 문법 상자 1 · 튜플에서 번호로 꺼내기 `rule[4]`

- **튜플**: 값 여러 개를 괄호 `( )` 로 묶은 것입니다. 규칙 한 줄을 이렇게 씁니다.
- 번호는 **0 번부터** 셉니다. 첫 값이 `rule[0]` 이고, 다섯 번째 값이 `rule[4]` 입니다.

```python
rule = (1, "outside", "DMZ", 443, "permit")   # 값 다섯 개를 하나로 묶은 튜플
print(rule[0])                                 # 첫 번째 값
print(rule[4])                                 # 다섯 번째 값

# 1
# permit
```

- 오늘 코드에서는 `rule[0]` 이 규칙 번호이고, `rule[4]` 가 동작(`permit` / `deny`)입니다.

#### 🐍 문법 상자 2 · 튜플을 한 번에 이름으로 풀기 `no, r_src, … = rule`

- 번호로 하나씩 꺼내는 대신, 값 다섯 개를 **이름 다섯 개에 한 번에** 나눠 담습니다.
- 이름의 개수와 튜플 값의 개수가 같아야 합니다.

```python
rule = (1, "outside", "DMZ", 443, "permit")
no, r_src, r_dst, r_port, action = rule   # 다섯 값을 다섯 이름에 나눠 담는다
print(no, action)

# 1 permit
```

- 오늘 코드의 `match_rule` 이 이 방법으로 규칙을 풉니다.

#### 🐍 문법 상자 3 · 값 두 개 리턴하고 받기 `return a, b` · `x, y = f()`

- 함수는 값을 **쉼표로 이어서 두 개** 리턴할 수 있습니다. 받는 쪽도 이름 두 개로 받습니다.
- 이름 하나로 받으면 두 값이 **튜플 하나**로 옵니다.

```python
def two():
    return "permit", 1        # 값 두 개를 한 번에 리턴한다

a, n = two()                  # 두 값을 a 와 n 에 나눠 담는다
print(a, n)
print(two())                  # 이름 하나로 받으면 튜플로 나온다

# permit 1
# ('permit', 1)
```

- 오늘 코드의 `judge` 가 동작과 규칙 번호를 이렇게 두 개 리턴합니다.

### 정답 4-1

💻 **터미널에 입력합니다.**

```bash
python day05_4-1_zone_rules.py
```
맥북: `python3 day05_4-1_zone_rules.py`

**나와야 하는 출력**

```
outside → DMZ 443 : permit (규칙 1)
outside → DMZ 80 : deny (규칙 0)
inside → DMZ 443 : permit (규칙 0)
DMZ → inside 445 : permit (규칙 2)
DMZ → inside 3389 : deny (규칙 0)
outside → inside 445 : deny (규칙 0)
```

**주석을 단 전체 코드**

```python
# 방화벽 규칙표: (번호, 출발 구역, 도착 구역, 포트, 동작) 튜플을 모은 리스트이다
RULES = [
    (1, "outside", "DMZ", 443, "permit"),    # 규칙 1: 인터넷에서 DMZ 의 443 번을 허용한다
    (2, "DMZ", "inside", 445, "permit"),     # 규칙 2: DMZ 에서 내부망의 445 번을 허용한다
]

def default_policy(src, dst):                # 규칙에 맞는 것이 없을 때의 기본 정책 함수이다
    if src == dst:                           # 출발 구역과 도착 구역이 같으면
        return "permit"                      # 허용한다
    if src == "inside":                      # 내부망에서 출발하면
        return "permit"                      # 허용한다
    if dst == "outside":                     # 인터넷으로 나가는 통신이면
        return "permit"                      # 허용한다
    return "deny"                            # 나머지는 모두 차단한다

def match_rule(rule, src, dst, port):        # 규칙 하나가 요청과 맞는지 알아보는 함수이다
    no, r_src, r_dst, r_port, action = rule  # 튜플 다섯 값을 각각 이름으로 꺼낸다
    return r_src == src and r_dst == dst and r_port == port   # 셋 다 같으면 True, 아니면 False 를 리턴한다

def judge(src, dst, port):                   # 요청 하나를 규칙표 위에서부터 판정하는 함수이다
    for rule in RULES:                       # 규칙을 위에서부터 하나씩 꺼낸다
        if match_rule(rule, src, dst, port): # 이 규칙이 요청과 맞으면
            return rule[4], rule[0]          # 규칙의 동작과 규칙 번호를 함께 리턴하고 함수를 끝낸다
    return default_policy(src, dst), 0       # 맞는 규칙이 없으면 기본 정책의 동작과 번호 0 을 리턴한다

TESTS = [                                    # 시험 요청 여섯 개: (출발, 도착, 포트)
    ("outside", "DMZ", 443),
    ("outside", "DMZ", 80),
    ("inside", "DMZ", 443),
    ("DMZ", "inside", 445),
    ("DMZ", "inside", 3389),
    ("outside", "inside", 445),
]

for src, dst, port in TESTS:                 # 시험 요청을 하나씩 꺼내 출발 · 도착 · 포트 로 나눈다
    action, no = judge(src, dst, port)       # judge 가 리턴한 두 값을 action 과 no 에 나눠 담는다
    print(src, "→", dst, port, ":", action, "(규칙 " + str(no) + ")")   # 판정 결과를 한 줄로 출력한다
```

**결과**

- (가) `default_policy` 는 규칙에 맞는 것이 없을 때의 **기본 정책**(같은 구역 · 내부망 출발 · 인터넷으로 나감은 허용, 나머지는 차단)을 알려 줍니다. `match_rule` 은 **규칙 하나가 요청과 맞는지** `True` / `False` 로 알려 줍니다.
- (나) 빈 주석 세 곳의 한 예는 위 코드의 `judge` 함수에 달린 주석입니다. 리턴값은 **동작(`permit` / `deny`)과 규칙 번호** 두 개입니다. 동작은 `rule[4]` 또는 `default_policy(...)`, 규칙 번호는 `rule[0]` 또는 `0` 입니다.
- (다) `return` 이 없으면 `for` 가 규칙을 끝까지 돌며, 맞는 규칙이 여러 개일 때 **위의 규칙이 아니라 마지막 규칙의 값**이 남을 수 있습니다. 방화벽은 **첫 번째로 맞는 규칙**을 쓰므로, 찾자마자 `return` 해서 함수를 끝내도록 했습니다.

**왜** — 규칙표는 위에서부터 첫 번째로 맞는 것이 결정합니다. `return` 은 그 「첫 번째」를 코드로 만든 것입니다.

**자주 틀리는 곳** — `judge` 가 값을 하나만 리턴한다고 쓰는 경우가 많습니다. `return rule[4], rule[0]` 처럼 값 두 개를 쉼표로 이어 리턴합니다. 「인터넷에서 DMZ 80 이 차단된 것은 규칙 1 때문」이라고 답하는 것도 틀립니다. 규칙 1 은 443 만 허용하고, 80 은 맞는 규칙이 없어 기본 정책으로 차단됩니다.

**관제에서는** — 로그에 규칙 번호 0(기본 정책) 판정이 많으면 규칙이 부족하다는 신호로 봅니다.

### 정답 4-2

💻 **터미널에 입력합니다.**

```bash
python day05_4-2_allowed_ports.py
```
맥북: `python3 day05_4-2_allowed_ports.py`

**채운 함수**

```python
def allowed_ports(src, dst, ports):
    result = []
    for port in ports:
        action, no = judge(src, dst, port)
        if action == "permit":
            result.append(port)
    return result
```

**나와야 하는 출력**

```
[443]
[445]
[22, 80, 443, 445, 3389]
[]
```

**결과**

- (가) 출력은 위 네 줄이고, 요구사항 표의 기대값과 같습니다. 함수는 위 「채운 함수」입니다.
- (나) 흐름 도식의 한 예:
  ```
  START
    │
    ▼
  [ take next rule ] ◄──────────┐
    │                           │
    ▼                           │
  [ match_rule ? ] ── no ───────┘
    │ yes
    ▼
  RETURN (rule action, rule no)

  (rules exhausted)
    │
    ▼
  RETURN (default_policy, 0)
  ```
- (다) `result = []` 를 `for` 위에 두어야 포트를 하나씩 보는 동안 **모은 값이 유지**됩니다. `for` 안에 두면 포트를 볼 때마다 리스트가 **비워져서** 마지막 포트 하나의 결과만 남습니다.
- (한 줄) 예: 「요구사항대로 인터넷은 DMZ 의 443 만, DMZ 는 내부망의 445 만 열려 있고 인터넷에서 내부망은 모두 막혀 있습니다.」

**왜** — 판정 함수를 포트 목록에 반복해서 부르면 통과하는 포트 목록이 나오고, 이 목록이 요구사항과 같은지가 점검 결과입니다.

**자주 틀리는 곳** — `if action == "permit"` 의 `==` 를 `=` 로 쓰면 에러가 납니다. `judge` 가 값 두 개를 리턴하므로 `action = judge(...)` 로 받으면 `action` 이 튜플이 되어 `"permit"` 과 같지 않습니다.

**관제에서는** — 규칙을 바꾼 뒤 같은 시험 요청으로 목록이 달라졌는지 비교하면, 의도하지 않게 열린 길을 찾을 수 있습니다.
