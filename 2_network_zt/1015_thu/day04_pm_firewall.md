### 5.1 규칙 한 줄 · 위에서부터 첫 번째로 맞는 규칙

**여기 나오는 말**

- **방화벽 (firewall)** (파이어월)
  - 망과 망 사이에서 요청마다 **허용할지 차단할지** 규칙으로 정하는 장비 · 프로그램
- **방화벽 규칙 (rule)** (룰)
  - 「누가(출발지) · 어디로(목적지) · 어느 포트로 가는 요청을 · 허용 / 차단한다」를 적은 **한 줄**
  - 실제 장비에는 프로토콜(TCP · UDP)도 적는다. 오늘은 모두 TCP 라 생략한다
- **첫 번째 일치 (first match)** (퍼스트 매치)
  - 규칙표를 **위에서부터** 읽다가 **처음 맞는 규칙** 하나로 결정하고, 그 아래는 보지 않는 방식
- **`any`** (애니)
  - 어떤 값이든 맞는다는 뜻. 방화벽 규칙의 누가 · 어디로 · 포트 어느 칸에도 쓴다. 우리말로는 「모든 곳」 · 「모든 포트」
- **맞는 규칙이 하나도 없을 때의 동작**
  - 장비 설정에 따라 **허용일 수도, 차단일 수도** 있다. 그래서 규칙표 맨 아래에 「모두 차단」을 직접 적어 둔다

**5교시 규칙표** (영어로 ruleset · 룰셋) — 위에서부터 한 줄이 한 문장입니다. 1번은 「직원이 업무 포털의 443번으로 가면 허용」이라는 뜻입니다.

| 번호 | 누가 | 어디로 | 포트 | 동작 |
|---|---|---|---|---|
| 1 | 직원 | 업무 포털 | 443 | 허용 |
| 2 | 직원 | 웹메일 | 443 | 허용 |
| 3 | 부산 지점 | 업무 포털 | 443 | 허용 |
| 4 | 업무 포털 | 고객 DB | 3306 | 허용 |
| 5 | any | any | any | 차단 |

- `any` 는 어떤 값이든 맞습니다. 누가 칸의 `any` 는 누구든(모든 곳), 어디로 칸의 `any` 는 어디든, 포트 칸의 `any` 는 어떤 포트든 맞습니다.

**읽는 법** — 요청 하나를 규칙 1번부터 읽습니다. 「누가 · 어디로 · 포트」가 **셋 다 같은** 첫 줄의 동작(허용 / 차단)이 답이고, 그 아래 줄은 읽지 않습니다. 하나라도 다르면 다음 줄로 갑니다.

**풀이 예제** — 요청: 직원 → 웹메일 · 443

- 1번 (직원 → 업무 포털 · 443): 어디로가 다릅니다. 다음 줄로 갑니다.
- 2번 (직원 → 웹메일 · 443): 셋 다 같습니다. **답: 2번 · 허용.** 여기서 멈추고 3번 이후는 읽지 않습니다.

### 5.2 막힌 연결은 패킷으로 어떻게 보이나

10/12 에 Wireshark 로 **성공한** 연결의 3-way handshake(SYN → SYN/ACK → ACK)를 봤습니다. 방화벽이 연결을 막으면 이 연결 과정이 중간에서 멈춥니다. 막는 방식은 두 가지입니다.

| 막는 방식 | 방화벽이 하는 일 | Wireshark 에 보이는 것 | 내 PC 쪽 결과 |
|---|---|---|---|
| **드롭 (drop)** (드롭) | 받은 SYN 을 **알리지 않고 버린다** | 내 SYN 만 다시 나가고 답이 없다 — `[TCP Retransmission]` | 기다리다가 시간 초과 |
| **거부 (reject)** (리젝트) | 「연결 안 받는다」고 **RST 를 보낸다** | SYN 바로 뒤에 상대의 RST | 곧바로 실패 |

- **재전송 (retransmission)** (리트랜스미션) — 답이 없어서 같은 패킷을 다시 보내는 것. 다시 보낼수록 **기다리는 시간이 점점 늘어난다**
- **RST** (리셋) — 연결을 거절한다는 신호
- **ECE · CWR** — 맥북이 SYN 에 붙이는 혼잡 표시. 이 실습에서는 무시해도 된다
- **RTT (Round Trip Time)** (알티티 · 왕복 시간) — 패킷이 갔다가 답이 돌아오기까지 걸린 시간. SYN 과 SYN/ACK 사이의 시간이 곧 RTT 다
- 서버 프로그램이 꺼진 포트(닫힌 포트)도 보통 RST 로 답합니다(10/12). 그래서 **RST 만으로는 방화벽 때문인지 닫힌 포트 때문인지 바로 구분되지 않고**, 답이 아예 없으면 중간의 방화벽이 버렸을 가능성이 큽니다.

**드롭일 때 3-way handshake 는 어디서 멈추나**

정상 연결은 세 단계로 진행됩니다.

```
내 PC ── SYN ───────▶ 서버   # 연결을 시작하고 싶다고 요청
내 PC ◀─ SYN/ACK ─── 서버   # 서버가 요청을 받았고 연결할 준비가 됐다고 응답
내 PC ── ACK ───────▶ 서버   # 서버의 응답을 확인하고 연결을 시작
```

방화벽이 첫 번째 메시지인 SYN 을 드롭하면 첫 단계에서 멈춥니다.

```
내 PC ── SYN ──▶ [방화벽: 버림] ✗     SYN 이 서버에 닿지 않거나, 서버의 답이 돌아오지 않는다
내 PC ◀─ (아무것도 안 옴)
내 PC ── SYN ──▶ …                    답이 없어서 같은 SYN 을 다시 보낸다 (재전송)
```

- 첫 번째 메시지(SYN)가 사라져서 두 번째 단계(SYN/ACK)로 넘어가지 못합니다. 연결이 시작되지 않습니다.
- 방화벽이 SYN 에 「차단」이라고 답해 주는 것이 아니라 **알리지 않고 버립니다.** 그래서 내 PC 는 이유를 모른 채 같은 SYN 을 다시 보냅니다. 재전송은 한 번이 아니라 답이 올 때까지 여러 번이고, 횟수와 간격은 운영체제마다 다릅니다. 처음 SYN 뒤에 다시 보낸 SYN 마다 Wireshark 에 `[TCP Retransmission]` 줄이 생깁니다.
- 정리: 「SYN 만 반복되고 SYN/ACK 가 없다」 = 드롭 의심, 「SYN 바로 뒤에 RST」 = 거부 또는 닫힌 포트.

방화벽 로그의 「차단」 한 줄은 패킷으로 보면 이런 모습입니다.

```
방화벽 로그   14:05:03  차단  10.8.0.21:51710  →  10.10.20.9:22   규칙 5
내 PC 패킷    SYN → (응답 없음) → SYN 재전송 → (응답 없음) → …
```

- **첫 줄은 방화벽이 남긴 기록입니다.** `14:05:03` 시각에 `10.8.0.21` 의 PC(`51710` 은 이 연결에 PC 가 임시로 쓴 번호)가 `10.10.20.9` 의 `22` 번(SSH, 서버 원격 관리)으로 접속하려 했고, 규칙 5번에 맞아 **차단**했다는 뜻입니다.
- **둘째 줄은 같은 접속을 그 PC 에서 본 모습입니다.** SYN 을 보냈는데 응답이 없고, 다시 보냈는데 또 응답이 없습니다.
- 방화벽은 차단했다고 알려 주지 않고 SYN 을 버리기만 하므로, 로그에는 「차단」 한 줄이 남고 PC 에서는 「SYN 만 반복」으로 보입니다. 두 줄은 같은 일을 서로 다른 쪽에서 본 것입니다.

### ✍️ 문제 5-2 · 허용된 연결과 막힌 연결을 Wireshark 로 재 보기

**할 일** — 같은 서버 `example.com` 의 80번(웹 포트)과 81번(쓰지 않는 포트)에 연결을 시도하며 Wireshark 로 캡처하고, handshake 가 어디서 끊기는지와 RTT · 재전송 간격을 재어 보고서에 적습니다.

**왜 중요한가** — 「접속이 안 된다」는 문의가 오면 관제는 패킷으로 범위를 좁힙니다. 응답이 없으면(드롭) 중간 방화벽 규칙부터, RST 가 오면 서버의 포트 · 프로그램부터 봅니다. RTT 를 재면 연결 하나에 걸리는 시간이 정상인지도 판단할 수 있습니다.

**상황** — 직원이 「회사 웹사이트(80번)는 열리는데, 새로 만든 관리 화면(81번)은 안 열려요」라고 신고했습니다. 방화벽 로그에는 `차단` 한 줄뿐입니다. 이 차단이 패킷으로는 어떻게 보이는지, 정상 연결과 나란히 놓고 확인합니다. 이번 실습에서는 `example.com` 을 회사 서버로 보고, **같은 서버의 80번과 81번**에 연결해 비교합니다.

**왜 80번과 81번인가**

```
내 PC ──▶ [서버 앞의 방화벽] ──▶ 서버
          규칙: 80번 허용
                그 밖의 포트는 차단 (맨 아래 「모두 차단」)
```

| 포트 | 왜 고르나 | 5.1 규칙표로 보면 |
|---|---|---|
| 80 | 웹 서버가 받는 정해진 번호라 방화벽이 **허용**해 둔 포트 | 허용 규칙에 맞음 |
| 81 | 아무 서비스도 쓰지 않는 번호라 방화벽 **규칙에 없는** 포트 | 맨 아래 「모두 차단」에 맞음 |

- 같은 PC, 같은 서버, 같은 `curl` 이고 **포트 번호만 다릅니다.** 그래서 두 결과의 차이는 방화벽 규칙 때문이라고 판단할 수 있습니다.
- `example.com` 앞에서 실제로 81번을 버리는 장비가 무엇인지는 우리 쪽에서 볼 수 없습니다. 우리는 **내 PC 에서 보이는 패킷**만 봅니다.

**이 문제에 나오는 말**

- **`tcp.port == 80 || tcp.port == 81`**
  - Wireshark 화면 필터. 포트 번호가 80 또는 81 인 패킷만 보여 준다
- **`curl`** (컬)
  - 주소를 주면 그 서버에 접속해 응답을 가져오는 명령. 접속할 때 TCP 연결(3-way handshake)을 먼저 만든다
- **`-m 15`**
  - 15초까지만 기다리고 끝내라는 옵션. 재전송이 여러 번 보이도록 넉넉히 기다린다
- **주소 뒤의 포트 번호**
  - `http://` 주소에 포트를 안 적으면 **80번**으로 접속한다. 포트를 바꾸려면 주소 뒤에 `:81` 처럼 콜론과 번호를 붙인다
- **80번 · 81번 포트**
  - 80번은 일반적인 웹(HTTP) 포트, 81번은 일반 웹 서버가 쓰지 않는 번호다. 이 서버는 81번 연결에 응답하지 않는다

**순서**

1. **[Wireshark]** 캡처를 시작합니다.
   - Wireshark 시작 화면이면 어댑터 목록에서 인터넷에 연결된 어댑터를 **더블클릭**합니다. 학원 PC 는 보통 `이더넷 2`, 맥북은 `Wi-Fi: en0` 입니다. 이름이 다르면 **오른쪽에 움직이는 선(그래프)이 보이는 어댑터**가 지금 통신 중인 어댑터입니다.

2. **[Wireshark]** 도구 줄 바로 아래 필터 칸에 아래를 입력하고 Enter 를 누릅니다. 칸이 초록인지 확인합니다.
   - ⚠ <mark style="background:#ffcdd2; color:#1a1a1a; padding:0 4px; border-radius:3px">아직 80번 · 81번 패킷이 없어서 목록이 비어도 정상입니다.</mark> 아래 3번에서 `curl` 을 치면 그때 줄이 생깁니다. 지금 비어 있다고 멈추지 않습니다.
   ```
   tcp.port == 80 || tcp.port == 81
   ```
3. **[터미널]** 캡처가 **돌아가는 동안** 80번(허용)에 연결합니다. HTML 글자가 나오면 연결된 것입니다. 연결이 만들어지면 웹 서버가 웹 페이지(HTML)를 응답으로 보내고, curl 이 그것을 화면에 그대로 출력하기 때문입니다.
   ```bash
   curl -m 15 http://example.com
   ```
   `http://` 주소에 포트를 안 적었으므로 curl 은 **80번 포트**로 접속합니다. 이 명령은 `example.com` 서버의 80번에 SYN 을 보내 연결을 시작합니다.

   이때 일어난 일입니다. SYN 이 방화벽의 허용 규칙을 통과해 서버에 닿았고, 서버가 SYN/ACK 로 답했습니다.
   ```
   내 PC ──SYN──────▶ [방화벽: 80번 허용] ──▶ 서버
   내 PC ◀─SYN/ACK─── [방화벽] ◀───────────── 서버      ← Wireshark 에 SYN/ACK 가 보인다
   ```
4. **[Wireshark]** `Info` 에 `[SYN]` 이 붙은 줄(내 PC → 서버)과 `[SYN, ACK]` 가 붙은 줄(서버 → 내 PC)을 찾아 두 줄의 `Time` 값을 적어 두고, 서버 IP 주소도 적어 둡니다. 서버 IP 는 **내 PC 가 보낸 `[SYN]` 줄**의 `Destination` 에 있습니다. 이 IP 를 적어 두는 이유는 5번에서 **같은 서버의 81번**에 연결하려면 이름(`example.com`) 대신 IP 를 써야 하기 때문입니다. 이름으로 접속하면 서버의 IP 여러 개를 번갈아 시도해서 80번과 81번이 다른 서버로 가거나 Wireshark 줄이 섞입니다.
   - `Source` 는 보낸 쪽이고 `Destination` 은 받는 쪽입니다. 줄 두 개는 방향이 반대입니다.
     ```
     Source      Destination   Info
     내 PC       서버 IP       51234 → 80 [SYN]            ← 이 줄의 Destination(서버 IP)을 적습니다
     서버 IP     내 PC         80 → 51234 [SYN, ACK]       ← 이 줄의 Destination 은 내 PC 주소입니다. 적지 않습니다
     ```
   - **어느 줄인지 고르는 방법** (하나만 맞으면 됩니다)
     - `Info` 에서 화살표 **뒤가 80** 인 줄(`내포트 → 80`)입니다. 화살표 앞이 80 인 줄(`80 → 내포트`)은 서버가 보낸 줄입니다.
     - `Info` 에 `[SYN]` 만 있고 `ACK` 가 없는 줄입니다. `[SYN, ACK]` 는 서버가 답한 줄입니다.
     - `Source` 가 내 PC 주소(윈도는 `ipconfig`, 맥북은 `ifconfig` 에 나오는 IPv4)와 같은 줄입니다.
   - **맞는지 확인하는 방법:** 적은 서버 IP 가 터미널에서 `nslookup example.com` 을 쳤을 때 나오는 주소(점으로 구분된 숫자 네 개) 가운데 하나와 같으면 맞습니다. 내 PC 주소를 적었다면 같지 않습니다.
   - 맥북은 `[SYN]` 줄이 `[SYN, ECE, CWR]` 로, `[SYN, ACK]` 줄이 `[SYN, ACK, ECE]` 로 보일 수 있습니다. `SYN` 이 들어 있으면 같은 줄입니다.
   - `Destination` 열의 IP 가 `104.20.23.1…` 처럼 잘려 보이면 열 제목 `Destination` 오른쪽 경계를 오른쪽으로 끌어 넓히거나, 그 줄을 클릭하고 아래 상세 창에서 IP 를 읽습니다.
   - `Destination` 에 `2606:` 처럼 콜론이 있는 긴 주소(IPv6)가 보이면, 점으로 구분된 숫자 네 개(IPv4)가 보이는 줄을 찾습니다. IPv4 줄이 없으면 3번을 `curl -4 -m 15 http://example.com` 으로 다시 칩니다.
   - `Time` 열은 캡처를 시작한 뒤 지난 초입니다. `14:05:03` 같은 시각으로 보이면 위쪽 메뉴 **View › Time Display Format › Seconds Since Beginning of Capture** 를 고릅니다.
5. **[터미널]** 같은 서버의 81번(막힘)에 연결합니다. 아래 명령의 `IP주소` 를 **4번에서 적은 서버 IP**(점으로 구분된 숫자 네 개, 예: `104.20.23.154`)로 바꿔서 칩니다. `IP주소` 라는 글자를 그대로 치지 않습니다.
   ```bash
   curl -m 15 http://IP주소:81
   ```
   - 이름(`example.com`) 대신 IP 를 쓰는 이유: 이름으로 접속하면 서버의 IP 여러 개를 번갈아 시도해 줄이 섞이기 때문입니다.
   - 주소 끝의 `:81` 이 **81번 포트**로 접속하라는 뜻입니다. 3번과 같은 서버이고 포트 번호만 다릅니다. 이 명령은 서버의 81번에 SYN 을 보냅니다.
   - 결과: HTML 은 나오지 않고 15초 뒤 마지막 줄에 `curl: (28) …` 오류 문구가 나옵니다.
   - 내 PC 주소를 넣으면 15초가 아니라 2초쯤에 `curl: (7)` 로 끝납니다. 이때는 IP 를 다시 확인합니다.

   이때 일어난 일입니다. 81번으로 보낸 SYN 에 서버의 답이 돌아오지 않았고, 내 PC 는 같은 SYN 을 다시 보냅니다.
   ```
   내 PC ──SYN──▶ [방화벽: 규칙에 없음 → 버림] ✗      서버의 답이 돌아오지 않는다
   내 PC ◀─(아무것도 안 옴)                          ← 그래서 SYN 이 다시 나간다(재전송)
   ```
6. **[Wireshark]** 오류 문구가 나온 뒤에 빨간 네모를 눌러 캡처를 멈춥니다. `Info` 에 `→ 81` 이 있는 줄을 모두 찾아 몇 줄인지, `[TCP Retransmission]` 이 붙었는지, 줄마다 `Time` 열 값을 적어 둡니다.
   - 필터가 포트 80 도 보여 주므로 **다른 프로그램의 80번 연결**(예: 다른 IP 로 가는 `[FIN, ACK]` · 빨간 `[RST]` 줄)이 같이 보일 수 있습니다. 내가 `curl` 로 보낸 IP 가 아니면 무시하고, `→ 81` 줄만 읽습니다.
   - 줄 색: 맨 처음 `[SYN…]` 줄(맥북은 `[SYN, ECE, CWR]`)은 회색, 다시 보낸 `[TCP Retransmission]` 줄은 붉은 계열(검은 바탕에 분홍 · 빨강 글자 등 화면 설정에 따라 다름)로 보입니다.
   - `→ 81` 줄은 이렇게 읽습니다.
     - **회색 `[SYN…]` 줄:** 내 PC 가 서버의 81번 포트에 **처음 연결을 요청한 줄**입니다. 출발지 포트 번호는 PC 가 이 연결에 임시로 쓴 번호입니다.
     - **붉은 계열 `[TCP Retransmission]` 줄:** 응답이 없어서 내 PC 가 **같은 요청을 다시 보낸 줄**입니다. 줄이 여러 개면 그만큼 다시 보낸 것입니다.
     - **서버가 보낸 줄이 있는지 봅니다.** `→ 81` 줄 가운데 서버 쪽에서 오는 `[SYN, ACK]` 나 `[RST]` 가 **하나도 없으면** 서버의 응답이 이 캡처에 보이지 않는 것이고, 5.2 의 **드롭**(알리지 않고 버림)으로 해석합니다.
     - 반대로 SYN 바로 뒤에 `[RST]` 가 보이면 드롭이 아니라 **거부 또는 닫힌 포트**입니다. 80번 줄처럼 `[SYN, ACK]` 가 오면 연결이 만들어진 것입니다.
   - **무엇이 막혔는지 정리합니다.**
     - **막힌 것:** 81번 포트로 보낸 **연결 요청(SYN)** 입니다. 서버에 닿지 않거나 서버의 답이 돌아오지 않아 연결이 만들어지지 않습니다.
     - **막히지 않은 것:** 같은 PC · 같은 서버 · 같은 `curl` 로 보낸 **80번 연결 요청**입니다. `[SYN, ACK]` 가 돌아와 연결이 만들어졌습니다.
     - **원인이 아닌 것:** 내 PC(80번은 연결됨)와 서버 자체(80번에 응답함)입니다. 서버는 켜져 있습니다.
     - **어디서 막혔는지:** 이 실습의 패킷으로 알 수 있는 것은 「내 PC 와 서버 사이 어딘가의 방화벽이 81번 SYN 을 버렸다」까지이고, 어느 장비인지는 알 수 없습니다. 이 실습에서는 `example.com` 을 회사 서버로 보고, 서버 앞 방화벽의 규칙에 81번 허용이 없어서 5.1 규칙표의 맨 아래 `any` 차단 줄에 걸린 것으로 읽습니다.
     ```
     80번   내 PC ──SYN──▶ [방화벽: 80번 허용] ──▶ 서버      내 PC ◀─SYN/ACK── 연결됨
     81번   내 PC ──SYN──▶ [방화벽: 규칙에 없음 → 버림] ✗    (서버 답 없음 → SYN 재전송 → 15초 뒤 curl (28))
     ```

### 왜 필요한가

1. 규칙표를 만드는 방식은 둘입니다. **허용할 것만 적고 나머지를 막거나**, **막을 것만 적고 나머지를 허용**합니다. 어느 쪽이냐에 따라 「적지 않은 것」이 열리기도 하고 닫히기도 합니다.
2. 방화벽 설정은 밖에서 볼 수 없지만, 포트를 하나씩 시험하면 어떤 방식인지 짐작할 수 있습니다. 실무에서는 새 서비스를 열기 전에 「이 포트가 밖으로 나가는지」를 이렇게 먼저 확인합니다.
3. 첫 번째 일치 방식이라 **같은 규칙도 순서가 바뀌면 결과가 달라집니다.** 「허용 규칙을 넣었는데 왜 막히지?」의 대부분이 순서 문제입니다.

### 6.1 허용 목록과 차단 목록

**여기 나오는 말**

- **허용 목록 (whitelist · allowlist)** (화이트리스트 · 얼라우리스트)
  - **허용할 통신만** 규칙으로 적고, 맨 아래에서 나머지를 **모두 차단**하는 방식
- **차단 목록 (blacklist · denylist)** (블랙리스트 · 디나이리스트)
  - **막을 통신만** 규칙으로 적고, 맨 아래에서 나머지를 **모두 허용**하는 방식
- **최소 권한 (least privilege)** (리스트 프리빌리지)
  - 업무에 **꼭 필요한 접근만** 주는 원칙. 방화벽에서는 허용 목록이 이 원칙을 따른다

| | 허용 목록 | 차단 목록 |
|---|---|---|
| 규칙에 적는 것 | 허용할 통신 | 막을 통신 |
| 맨 아래 줄 | 모두 **차단** | 모두 **허용** |
| 규칙에 없는 새 서버 · 새 포트 | 막힌다 | **열린다** |

### 6.2 방화벽 정책은 밖에서 시험해 봅니다

**이 실습을 왜 하나**

- 방화벽의 설정 파일은 볼 수 없는 경우가 많습니다(고객사 · 학원). 설정을 못 봐도 **밖에서 포트를 하나씩 시험하면 어떤 정책인지 짐작**할 수 있습니다.
- 알아내려는 것은 이 방화벽이 6.1 의 **허용 목록**(필요한 것만 열고 나머지는 차단)인지 **차단 목록**(위험한 것만 막고 나머지는 허용)인지입니다.
- 5-2 는 서버로 들어오는 쪽을 봤고, 이번에는 **내 PC 에서 밖으로 나가는** 연결을 시험합니다.
- 그래서 포트를 세 개만 고릅니다. 하나는 **열려 있어야 하는 것**(기준점), 둘은 **위험해서 막는 곳이 많은 것**입니다.
  - `443` 웹: 수업에 필요해서 열려 있어야 합니다. 기준점입니다.
  - `445` 파일 공유(SMB): 학원 밖으로 쓸 일이 없고 공격에 자주 쓰여서 막는 곳이 많습니다.
  - `3389` 원격 데스크톱(RDP): 관리용이라 밖에서 열려 있으면 위험합니다.
- 결과를 이렇게 읽습니다. 웹만 열리고 `445` · `3389` 가 모두 막히면 **허용 목록**에 가깝고, 위험한 포트가 열려 있거나 일부만 막히면 **차단 목록**에 가깝습니다.
- 실무에서는 새 서비스를 열기 전이나 고객사를 점검할 때 「이 포트가 밖으로 나가는지」를 이렇게 확인합니다.

**여기 나오는 말**

- **portquiz.net** (포트퀴즈)
  - **아무 포트로 접속해도 응답하도록** 공개된 시험용 사이트. 여기에 접속이 안 되는 포트가 있으면 사이트가 아니라 **내 쪽 방화벽이 막은 것**이다
- **`tcp.port == 443 || tcp.port == 445 || tcp.port == 3389`**
  - 한마디로 **세 포트(443 · 445 · 3389)로 오가는 패킷만 보여 주는** Wireshark 화면 필터
  - 조각으로 읽습니다
    - `tcp.port == 443`: TCP 패킷의 포트가 443 이다
    - `||`: 「또는」. 세 조건 가운데 **하나라도 맞으면** 보여 준다
  - 그래서 「포트가 443 이거나, 445 이거나, 3389 인 패킷」이 모두 보입니다
  - `tcp.port` 는 **출발지 포트와 목적지 포트를 모두** 봅니다. 내 PC 가 보낸 요청(목적지 포트 443)과 서버가 보낸 답(출발지 포트 443)이 **둘 다 보입니다**
  - 이 필터가 없으면 PC 가 주고받는 다른 패킷이 섞여 보여서, 실습한 세 포트의 줄을 찾기 어렵습니다
  - 5-2 의 `tcp.port == 80 || tcp.port == 81` 과 같은 방식이고, 포트만 세 개로 늘었습니다
- **`tcp.flags.syn == 1 && tcp.flags.ack == 0`**
  - 한마디로 **「연결해 주세요」라는 첫 요청(SYN)만 보여 주는** Wireshark 화면 필터
  - 연결을 만드는 과정에서 패킷이 세 번 오갑니다: ① SYN (연결하자) → ② SYN/ACK (알겠다) → ③ ACK (확인)
  - 패킷에는 SYN · ACK 라는 **표시(플래그)** 가 있고, 켜져 있으면 `1`, 꺼져 있으면 `0` 입니다
    - ① SYN: SYN 만 켜짐 (SYN `1` · ACK `0`)
    - ② SYN/ACK: 둘 다 켜짐 (SYN `1` · ACK `1`)
    - ③ ACK 와 그 뒤의 데이터: SYN 꺼짐 (SYN `0`)
  - 그래서 「SYN 이 켜져 있고(`syn == 1`) **그리고**(`&&`) ACK 는 꺼져 있다(`ack == 0`)」를 찾으면 **①번만** 남습니다
  - 한 PC 가 여러 포트로 연결을 시작하는 모습을 볼 때 쓴다
- **`tcp.analysis.retransmission`**
  - 한마디로 **「답이 없어서 다시 보낸 패킷」만 보여 주는** Wireshark 화면 필터
  - 패킷을 보냈는데 답이 안 오면, PC 는 같은 패킷을 한 번 더 보냅니다. 이것을 **재전송**이라 합니다
  - Wireshark 는 다시 보낸 패킷의 `Info` 칸에 `[TCP Retransmission]` 이라고 적어 줍니다. 5-2 의 81번 줄에서 본 것과 같습니다
  - 이 필터는 그 표시가 붙은 줄만 남깁니다
    - 맨 처음 보낸 패킷: 표시가 없어서 **안 보입니다**
    - 다시 보낸 패킷: 표시가 있어서 **보입니다**
    - 답이 바로 온 연결: 다시 보낼 일이 없어서 **안 보입니다**
  - 그래서 이 화면에 남은 줄 = 「답이 없었던 연결」입니다

⚠ 남의 서버에 여러 포트를 차례로 연결해 보는 것은 포트 스캔이라 허락 없이 하면 안 됩니다. portquiz.net 은 이런 시험을 하라고 공개된 곳이라 씁니다.

### ✍️ 문제 6-1 · 학원 방화벽은 허용 목록일까 차단 목록일까

**할 일** — Wireshark 를 켠 채 portquiz.net 의 포트 세 개에 차례로 연결해, 포트마다 열림 · 드롭 · 거부를 표로 판정하고, 학원 방화벽이 6.1 의 어느 방식에 가까운지 근거와 함께 추론합니다.

**왜 중요한가** — 고객사 방화벽 설정을 볼 수 없을 때도 밖에서 포트를 시험하면 어떤 정책인지 짐작할 수 있습니다. 새 서비스를 열기 전에 포트가 나가는지 확인하는 일은 운영에서 자주 합니다.

**상황** — 5-2 에서는 서버 앞의 방화벽을 봤습니다. 이번에는 반대로 **내 PC 앞의 방화벽**, 곧 학원 방화벽이 어느 포트를 밖으로 내보내 주는지 알아냅니다. 설정은 볼 수 없으니, 시험용 사이트에 포트를 하나씩 연결해 보고 응답이 오는지로 추측합니다.

```
내 PC ──SYN(연결 요청)──▶ [학원 방화벽] ──▶ 인터넷 ──▶ portquiz.net (모든 포트에 응답하는 사이트)
내 PC ◀──SYN/ACK(응답)── [학원 방화벽] ◀── 인터넷 ◀── portquiz.net      ← 방화벽이 통과시킨 포트만 응답이 돌아옴
```

- portquiz.net 은 **어느 포트로 접속해도 응답**합니다. 그래서 응답이 없으면 사이트가 아니라 **그 사이의 학원 방화벽**이 막은 것입니다. 5-2 에서 「같은 서버의 80번이 응답했으니 81번의 무응답은 방화벽」이라고 판단한 것과 같은 순서입니다.

**왜 이 세 포트인가**

| 포트 | 쓰는 곳 | 시험하기 전의 예상 |
|---|---|---|
| 443 | 웹 접속(HTTPS) | 열려 있을 것 — 수업에 필요. 기준점 |
| 445 | SMB (Windows 파일 공유) | 막혀 있을 수 있음 — 학원 밖으로 파일을 공유할 일이 없고 공격에 자주 쓰임 |
| 3389 | RDP (Windows 원격 데스크톱) | 막혀 있을 수 있음 — 관리용 |

위 표는 시험하기 전의 **예상**일 뿐입니다. 실제로 열려 있는지는 아래에서 시험해 확인합니다.

- 웹 포트만 열리고 파일 공유 · 원격 접속 포트가 막히면 허용 목록에 가깝고, 모두 열리면 차단하는 것이 거의 없는 차단 목록에 가깝습니다(6.1).

**순서**

1. **[Wireshark]** 5-2 의 캡처가 돌아가는 중이면(빨간 네모가 빨간색) 빨간 네모를 눌러 멈춥니다. 그다음 도구 줄 맨 왼쪽의 **상어 지느러미 모양 시작 단추**를 눌러 같은 어댑터로 캡처를 새로 시작합니다. 저장 창이 뜨면 「저장하지 않고 계속」(맥북은 `Continue without Saving`)을 누릅니다. 5-2 의 패킷은 지워집니다.
2. **[Wireshark]** 도구 줄 바로 아래 필터 칸에 아래를 입력하고 Enter 를 누릅니다. 칸이 초록인지 확인합니다. 세 포트의 패킷만 보입니다.
   ```
   tcp.port == 443 || tcp.port == 445 || tcp.port == 3389
   ```
   - 이 필터는 「포트가 443 **또는** 445 **또는** 3389 인 패킷」만 남깁니다. `||` 가 「또는」입니다.
   - 아직 `curl` 을 치지 않았으니 목록이 비어 있어도 정상입니다. 3번에서 연결하면 줄이 생깁니다.
3. **[터미널]** 캡처가 **돌아가는 동안** 포트 세 개에 차례로 연결합니다. 열린 포트는 `Port test successful!` 이 나옵니다. 막힌 포트는 5초 뒤 마지막 줄에 `curl: (28) …` 오류 문구가 나오고(드롭), 거부된 포트는 5초를 기다리지 않고 바로 `curl: (7) …` 로 끝납니다.
   ```bash
   curl -m 5 http://portquiz.net:443
   curl -m 5 http://portquiz.net:445
   curl -m 5 http://portquiz.net:3389
   ```
   포트마다 이렇게 둘 중 하나로 보입니다.
   ```
   열린 포트    내 PC ──SYN──▶ [학원 방화벽: 통과] ──▶ portquiz ──SYN/ACK──▶ 내 PC
   막힌 포트    내 PC ──SYN──▶ [학원 방화벽: 버림] ✗     (답 없음 → SYN 재전송 → 5초 뒤 curl 종료)
   ```
4. **[Wireshark]** 세 번째 연결의 결과가 나온 뒤 빨간 네모로 캡처를 멈춥니다. 포트마다 아래 필터를 **하나씩** 필터 칸에 붙여 넣고 Enter 를 눌러 열림 · 거부 · 드롭을 구분합니다. 필터를 바꿀 때는 이전 필터를 지우고 붙여 넣습니다. 칸이 초록인지 확인합니다.
   ```
   tcp.port == 443 && (tcp.flags.syn == 1 || tcp.flags.reset == 1)
   ```
   - 열림: `내포트 → 443 [SYN]` 줄 다음에 `443 → 내포트 [SYN, ACK]` 줄
   - 거부: `내포트 → 443 [SYN]` 줄 다음에 `443 → 내포트 [RST, ACK]` 줄
   - 드롭: `내포트 → 443 [SYN]` 줄과 `[TCP Retransmission] 내포트 → 443 [SYN]` 줄만 반복되고, `443 →` 로 시작하는 줄이 없음
   ```
   tcp.port == 445 && (tcp.flags.syn == 1 || tcp.flags.reset == 1)
   ```
   - 열림: `내포트 → 445 [SYN]` 줄 다음에 `445 → 내포트 [SYN, ACK]` 줄
   - 거부: `내포트 → 445 [SYN]` 줄 다음에 `445 → 내포트 [RST, ACK]` 줄
   - 드롭: `내포트 → 445 [SYN]` 줄과 `[TCP Retransmission] 내포트 → 445 [SYN]` 줄만 반복되고, `445 →` 로 시작하는 줄이 없음
   ```
   tcp.port == 3389 && (tcp.flags.syn == 1 || tcp.flags.reset == 1)
   ```
   - 열림: `내포트 → 3389 [SYN]` 줄 다음에 `3389 → 내포트 [SYN, ACK]` 줄
   - 거부: `내포트 → 3389 [SYN]` 줄 다음에 `3389 → 내포트 [RST, ACK]` 줄
   - 드롭: `내포트 → 3389 [SYN]` 줄과 `[TCP Retransmission] 내포트 → 3389 [SYN]` 줄만 반복되고, `3389 →` 로 시작하는 줄이 없음
   - `tcp.flags.syn == 1` 은 SYN 표시가 켜진 줄(`[SYN]` · `[SYN, ACK]`), `tcp.flags.reset == 1` 은 거절 신호 RST 가 켜진 줄입니다. 그래서 이 필터는 그 포트의 **연결 요청**(`[SYN]`), **서버의 응답**(`[SYN, ACK]`), **거부**(`[RST]`) 줄만 남깁니다. `&&` 는 「그리고」, `||` 는 「또는」입니다.
   - 열린 포트에서 연결이 만들어지는 과정은 `[SYN]` → `[SYN, ACK]` → `[ACK]` 세 줄이지만, 세 번째 `[ACK]` 줄은 이 필터에 걸리지 않아 **보이지 않는 것이 정상**입니다. 열린 포트는 `[SYN]` 과 `[SYN, ACK]` **두 줄**이 보입니다.
   - 방금 `curl` 로 보낸 연결은 화면의 **가장 아래쪽 줄**(`No.` 번호가 큰 쪽)입니다. 브라우저 등 다른 프로그램의 연결 줄이 위쪽에 섞여 있을 수 있습니다.
   - 포트마다 위 세 가지 가운데 어느 모양인지 보고 **열림 · 거부 · 드롭**을 정합니다. `내포트` 는 내 PC 가 이 연결에 임시로 쓴 번호(예: `51234`)라 줄마다 숫자로 보입니다. 맥북은 `[SYN]` 이 `[SYN, ECE, CWR]` 로 보일 수 있습니다.
   - 서버가 보낸 줄은 `Info` 에서 화살표 **앞이 그 포트 번호**입니다. 예: `443 → 51234 [SYN, ACK]`.
   - 줄의 정확한 포트 번호는 아래쪽 **패킷 상세 창**에서 확인합니다. 줄을 클릭한 뒤 `Transmission Control Protocol` 줄을 펼치면 `Source Port`(출발지 포트)와 `Destination Port`(목적지 포트)가 나옵니다.
5. **[Wireshark]** 필터 칸의 `X` 로 지운 뒤 아래 필터를 입력하고 Enter 를 눌러 재전송된 패킷만 봅니다. 여기 남은 줄의 목적지 포트가 「답이 없었던」 포트입니다.
   ```
   tcp.analysis.retransmission
   ```
   이 필터를 쓰면 화면이 이렇게 바뀝니다.
   - **남는 것:** 답이 없어서 다시 보낸 패킷. 줄 하나가 재전송 한 번입니다.
   - **사라지는 것:** 응답이 바로 온 연결(열린 포트)과 맨 처음 보낸 패킷.
   - **읽는 법:** 남은 줄의 목적지 포트가 「답이 없었던 포트」입니다. 한 포트에 줄이 여러 개면 그만큼 여러 번 다시 보낸 것입니다.
   - **줄이 하나도 없으면:** 다시 보낸 패킷이 없다는 뜻입니다. 세 포트 모두 답이 왔거나, `[RST]` 로 바로 거부됐을 수 있으니 4번의 포트별 필터 화면에서 `[RST]` 가 있었는지 봅니다.
   - **쓰는 곳:** 「접속이 느리다 · 안 된다」는 신고가 오면 재전송이 있는지 먼저 봅니다. 재전송이 계속되면 중간에서 패킷이 버려지는 것(방화벽 드롭 · 망 문제)을 의심합니다.
6. **[Wireshark]** 필터 칸의 `X` 로 지운 뒤 2번의 세 포트 필터를 다시 붙여 넣어 화면을 한 번 봅니다. 그다음 필터를 아래로 바꾸고 Enter 를 눌러 연결을 시작한 SYN 만 보며, 바뀌기 전 화면(2번 필터)과 무엇이 달라졌는지 봅니다.
   ```
   tcp.flags.syn == 1 && tcp.flags.ack == 0
   ```
   이 필터를 쓰면 화면이 이렇게 바뀝니다.
   - **남는 것:** 내 PC 가 보낸 「연결해 주세요」 줄(SYN). 답이 없어서 다시 보낸 SYN 도 같은 줄이라 남습니다.
   - **사라지는 것:** 서버가 보낸 답(`[SYN, ACK]` · `[RST]`)과 연결된 뒤의 데이터.
   - **읽는 법:** 목적지 포트가 다른 줄이 몇 종류인지 세면 「이 PC 가 포트를 몇 개 시도했는지」를 알 수 있습니다. 서버가 답했는지는 이 화면에서 안 보이므로 2번 필터 화면과 비교합니다.
   - **쓰는 곳:** 한 PC 가 짧은 시간에 여러 포트로 SYN 을 보내면 포트 스캔 의심입니다.

### 6.3 규칙 순서 — 넓은 규칙과 좁은 규칙

**규칙표에 주소를 적는 법** — 5교시 규칙표는 「직원」 · 「업무 포털」 같은 이름으로 적었습니다. 실제 방화벽 규칙에는 이름 대신 주소를 적습니다. 아래 6-2 와 7교시의 규칙표가 이 모양입니다. 5교시 표의 「누가」 칸은 「출발지」, 「어디로」 칸은 「목적지」라고 부릅니다.

**`/숫자` 읽는 법**

- `/32`: IP 주소 **1개만** 가리킵니다.
  - 예: 업무 포털 `10.10.20.5/32` → `10.10.20.5` 하나
- `/24`: 앞 세 자리는 고정하고 마지막 자리가 달라지는 **네트워크 범위**입니다. 7교시 코드의 `ip_network` 도 이 네트워크 범위를 뜻합니다.
  - 예: 직원(VPN) `10.8.0.0/24` → `10.8.0.0` ~ `10.8.0.255`. 부산 지점 `192.168.20.0/24` 도 같은 모양입니다.
- `/16`: 앞 두 자리를 고정합니다.
  - 예: 본사 전체 `10.10.0.0/16` → `10.10.0.0` ~ `10.10.255.255`
- `/0`: 범위를 전혀 제한하지 않는 **모든 IPv4 주소**입니다.
  - 예: `any`(모든 곳) `0.0.0.0/0`
- `/숫자`가 클수록 범위가 좁고, 작을수록 넓습니다. 범위에 들어 있는 주소 수: 업무 포털 `/32` 는 1개 → 직원 `/24` 는 256개 → 본사 전체 `/16` 은 65,536개 → `any` `/0` 은 전부입니다.

| 5교시의 이름 | 방화벽에 쓰는 주소 | 들어 있는 주소 |
|---|---|---|
| 직원 (VPN) | `10.8.0.0/24` | `10.8.0.0` ~ `10.8.0.255` |
| 부산 지점 | `192.168.20.0/24` | `192.168.20.0` ~ `192.168.20.255` |
| 업무 포털 | `10.10.20.5/32` | 이 주소 하나 |
| 웹메일 | `10.10.20.6/32` | 이 주소 하나 |
| 고객 DB | `10.10.30.7/32` | 이 주소 하나 |
| 관리 서버 | `10.10.20.9/32` | 이 주소 하나 |
| 보안팀 관리자 PC | `10.10.40.10/32` | 이 주소 하나 |
| `any` (모든 곳) | `0.0.0.0/0` | 어떤 주소든 |

- 요청의 출발지도 주소입니다. 직원이 VPN 을 켜면 PC 가 `10.8.0.x` 주소를 받아 「직원」에 해당하고, VPN 을 끄면 집 인터넷 주소(예: `211.36.10.7`)를 써서 `any` 에만 해당합니다.

- **넓은 규칙** — 많은 주소 · 포트에 맞는 규칙. 예: 목적지 `10.10.0.0/16` · 포트 `any`
- **좁은 규칙** — 적은 주소 · 포트에만 맞는 규칙. 예: 목적지 `10.10.20.5/32` · 포트 `443`

넓은 규칙이 좁은 규칙보다 **위에** 있으면, 좁은 규칙에 맞을 요청이 넓은 규칙에 먼저 맞아 좁은 규칙까지 내려가지 못합니다.

#### 🐍 문법 상자 · `for` 안의 `for` · `found = False` — 요청마다 규칙을 처음부터 읽는 판정 코드

손으로 한 판정은 「요청 하나를 규칙표 1번부터 차례로 비교하다가, 처음 맞는 규칙에서 멈춘다」였습니다. 코드도 같습니다. 바깥 `for` 는 요청을 하나씩, 안쪽 `for` 는 규칙을 위에서부터 하나씩 꺼내고, `found` 는 「이미 처음 맞는 규칙을 찾았는가」를 적어 둡니다. 10/13 오후 6-2 의 `found` 와 같은 방식이지만, 요청마다 다시 `False` 로 되돌리는 점이 다릅니다.

```python
RULES = [(1, "A"), (2, "B"), (3, "A")]   # (번호, 맞는 글자) 튜플 세 개로 된 연습용 규칙표를 RULES 에 담는다
for req in ["A", "B"]:                     # 바깥 반복: 요청 글자를 하나씩 req 에 담아 반복한다
    found = False                          # 요청마다 「아직 못 찾음」으로 다시 시작한다
    for no, letter in RULES:               # 안쪽 반복: 규칙을 위에서부터 하나씩 꺼낸다
        if found == False:                 # 아직 못 찾았을 때만 아래를 확인한다
            if letter == req:              # 규칙의 글자가 요청과 같으면 아래 두 줄을 실행한다
                print(req, "→ 규칙", no)   # 요청과 처음 맞은 규칙 번호를 출력한다
                found = True               # 찾았으므로 이 요청에서는 아래 규칙을 더 보지 않는다

# A → 규칙 1     ← 3번도 "A" 지만 이미 1번에서 찾아 출력하지 않는다
# B → 규칙 2
```

| 쓰는 것 | 뜻 |
|---|---|
| 바깥 `for` 안의 `found = False` | 요청이 바뀔 때마다 「못 찾음」으로 되돌린다. 바깥 `for` 위에 두면 둘째 요청부터는 아무 규칙도 확인하지 않는다 |
| `for no, letter in RULES:` | `RULES` 안의 `(1, "A")` 같은 묶음(튜플)을 하나씩 꺼내 `no` 와 `letter` 두 변수에 나눠 담는다 |
| `if found == False:` | 첫 번째로 맞는 규칙 하나만 쓰고, 그 뒤 규칙은 건너뛴다 — 첫 번째 일치 |
| `"10.8.0.0/24"` · `"10.10.20.5/32"` | 6.3 의 주소 표기. `/24` 는 `10.8.0.0` ~ `10.8.0.255`, `/32` 는 주소 하나 |
| `ipaddress.ip_address(주소) in ipaddress.ip_network(망)` | 주소가 그 망에 들어 있으면 `True` (10/13 오후) |
| `src_ok and dst_ok and port_ok` | 세 값이 모두 `True` 일 때만 `True` |
| `rport == "any" or rport == port` | 규칙의 포트가 `any`(모든 포트)이거나 요청의 포트와 같으면 `True` |

### ✍️ 문제 7-1 · 요구사항을 읽고 규칙표 직접 쓰기

**할 일** — 아래 요구사항 다섯 개를 지키는 규칙표를 `RULES` 에 직접 쓰고, 시험 요청 8개로 채점해 `점수: 8 / 8` 이 나올 때까지 고칩니다.

**왜 중요한가** — 고객사의 요구사항을 방화벽 규칙으로 옮기는 것이 네트워크 보안 운영의 기본 업무입니다. 시험 요청으로 채점하면 규칙이 너무 넓어 열린 곳과, 빠뜨려 막힌 곳을 바로 찾습니다.

**요구사항** (5교시 연습과 별개로 새로 정해진 요구사항입니다. 5교시의 규칙표를 그대로 베끼지 않고 아래 요구사항에 맞춰 씁니다.)

| # | 요구사항 |

| ② | 부산 지점(`192.168.20.0/24`)은 업무 포털과 웹메일의 HTTPS(`443`)**만** 쓴다 |

| ⑤ | 위에 없는 통신은 모두 막는다 — 규칙표 맨 아래 줄로 적는다 |

**순서**

   ```python
       for no, rsrc, rdst, rport, action in RULES:                     # 규칙을 위에서부터 하나씩 꺼낸다
           if found == False:                                          # 아직 못 찾았을 때만 아래를 확인한다
               src_ok = ipaddress.ip_address(src) in ipaddress.ip_network(rsrc)   # 출발지가 규칙의 출발지 망에 들어 있으면 True
               dst_ok = ipaddress.ip_address(dst) in ipaddress.ip_network(rdst)   # 목적지가 규칙의 목적지 망에 들어 있으면 True
               port_ok = rport == "any" or rport == port               # 규칙의 포트가 "any" 이거나 요청의 포트와 같으면 True
               if src_ok and dst_ok and port_ok:                       # 세 가지가 모두 맞으면 첫 번째로 맞은 규칙이다
                   result = action                                     # 그 규칙의 동작을 결과로 담는다
                   found = True                                        # 찾았으므로 아래 규칙은 더 보지 않는다
       if result == expect:                                            # 결과가 기대와 같으면 아래 두 줄을 실행한다
           score = score + 1                                           # 맞힌 수를 1 늘린다
           print("맞음  ", src, "→", dst, port, ":", result)            # 맞은 시험을 출력한다
       else:                                                           # 결과가 기대와 다르면 아래 줄을 실행한다
           print("틀림  ", src, "→", dst, port, ":", result, "/ 기대:", expect)  # 틀린 시험과 기대 결과를 함께 출력한다
   print("점수:", score, "/", len(TESTS))                              # 맞힌 수와 전체 시험 수를 출력한다
   ```

**관제에서는** — 「접속이 안 돼요」 문의가 오면 방화벽 로그에서 그 요청이 몇 번 규칙에 맞았는지 먼저 봅니다.

### 정답 5-2

💻 **터미널에 입력합니다.** (Wireshark 필터 `tcp.port == 80 || tcp.port == 81` 로 캡처하면서)

```bash
curl -m 15 http://example.com
curl -m 15 http://IP주소:81
```

**결과**

- (가-1) `51234 → 80 [SYN] …` 과 `80 → 51234 [SYN, ACK] …` 두 줄이고, `Time` 의 차이가 RTT 입니다(맥북 실측 예: 0.000 → 0.036 이면 36 ms, 사람마다 값이 다릅니다). 앞의 번호는 내 PC 의 임시 포트라 사람마다 다릅니다.
- (가-2) SYN 이 여러 번 나가고(맥북 실측: 15초 동안 8번, 목적지는 모두 같은 IP), 두 번째부터 `[TCP Retransmission]` 이 붙으며, 상대에게서는 아무것도 오지 않습니다. `curl` 은 15초 뒤 `curl: (28) Connection timed out …` 으로 끝납니다. 맥북에서는 81번에 응답이 한 번도 오지 않고 15초 뒤 종료 코드 28 로 끝납니다. 학원 PC(Windows)에서도 `curl: (28) Connection timed out after 15017 milliseconds` 로 끝났습니다(Windows 는 SYN 횟수가 더 적을 수 있습니다). RST 가 바로 오고 `Failed to connect` 로 끝났다면 「거부」 방식입니다.
- (나-1) 막힌 것은 81번 포트로 보낸 연결 요청(SYN)이고, 같은 서버의 80번은 막히지 않았습니다. 81번은 첫 단계 SYN 에서 멈췄습니다. SYN/ACK 가 오지 않아 handshake 의 둘째 단계로 가지 못했고, 응답 없이 재전송만 반복됐으므로 **드롭** 방식입니다(RST 가 왔다면 거부 방식).
- (나-2) 간격은 처음에는 같다가 점점 늘어납니다(맥북 실측: 1초 간격 다섯 번 뒤 2초, 4초. Windows 는 첫 재전송 시점과 간격이 다를 수 있습니다). 이유는 답이 없는 원인이 네트워크 혼잡일 수 있어서, 같은 간격으로 계속 다시 보내면 상황이 더 나빠지기 때문에 다시 보낼 때마다 기다리는 시간을 늘리는 것입니다.
- (다) `10.8.0.21` 의 PC 에서는 1초 간격으로 서로 다른 서버 · 포트(관리 서버 SSH · 관리 화면, 고객 DB, 새 DB)로 SYN 을 보내고 하나도 SYN/ACK 를 받지 못한 모습입니다. 관리용 · DB 포트를 1초 간격으로 차례로 시도한 것이라, 열린 곳을 찾는 내부 포트 스캔으로 보입니다. 다음에 확인할 기록은 오전 4교시에서 본 VPN 게이트웨이의 접속 로그입니다. 그 시각에 이 VPN 주소를 받은 사용자와 출발 공인 IP 를 찾습니다.
- (라) SYN 을 보냈는데 **응답이 전혀 없으면** 중간 방화벽이 버렸을 가능성이 큽니다(드롭). **RST 가 오면** 방화벽이 거부한 것일 수도, 서버에 닿았지만 그 포트를 받는 프로그램이 없는 것일 수도 있어 둘을 바로 구분할 수 없습니다. 서버의 포트 · 프로그램을 먼저 보고, 방화벽 규칙도 함께 확인합니다. **SYN/ACK 가 오면** 연결은 되었으니 방화벽이나 포트가 아니라 서버 프로그램의 응답이나 응용 계층 문제를 봅니다.

**왜** — 방화벽이 버리면 SYN/ACK 가 오지 않아 handshake 가 첫 단계에서 멈추고, 내 PC 는 같은 SYN 을 간격을 늘려 가며 다시 보내다가 시간 초과로 끝납니다.

**자주 틀리는 곳** — 시간 초과를 「인터넷이 끊겼다」 또는 「서버가 꺼졌다」로 적는 경우가 많습니다. 같은 서버의 80번은 바로 연결됐으므로 인터넷도 서버도 정상이고, 81번 포트만 막힌 것입니다.

**관제에서는** — 「접속이 안 된다」 문의에서 SYN 이 나가는데 답이 없으면 중간 방화벽 규칙부터, RST 가 오면 서버의 포트 · 프로그램 상태와 방화벽 거부 규칙을 함께 확인합니다.

### 정답 6-1

💻 **터미널에 입력합니다.** (Wireshark 필터 `tcp.port == 443 || tcp.port == 445 || tcp.port == 3389` 로 캡처하면서)

```bash
curl -m 5 http://portquiz.net:443
curl -m 5 http://portquiz.net:445
curl -m 5 http://portquiz.net:3389
```

**결과** — 학원망의 결과는 날마다 다를 수 있어서 **판단 기준**을 정답으로 둡니다.

- (가) 열린 포트는 `Port test successful!` 이 나오고 Wireshark 에 SYN/ACK 가 옵니다. 막힌 포트는 5초 뒤 `curl: (28) …` 오류 문구가 나오고, `tcp.analysis.retransmission` 필터에 그 포트의 줄이 남습니다(드롭). RST 가 바로 오고 `curl: (7) …` 로 빨리 끝나면 거부입니다. 학원 PC 에서 시험했을 때 **443 · 3389 는 열림**, **445 는 드롭**이었습니다. 이 학원망에서는 거부(RST)로 끝나는 포트가 나오지 않았습니다.
- (나) 웹(443)과 원격 데스크톱(3389)이 열리고 파일 공유(445)만 막혀 있으므로 **차단 목록에 가깝습니다.** 대부분의 포트가 열리고 위험하다고 알려진 몇 개만 막는 모습입니다. 만약 웹만 열리고 445 · 3389 같은 포트가 모두 막혔다면 허용 목록에 가깝습니다. 세 포트가 모두 열리면 이 시험만으로는 차단 규칙이 거의 없다고 볼 수 있습니다. portquiz.net 자체가 막혀 세 포트가 모두 드롭이면 「이 사이트를 막는다」는 뜻이라 방식은 알 수 없습니다.
- (다-1) 세 포트는 전체 65,535 개 가운데 일부뿐이고, 목적지가 portquiz.net 하나뿐이라 학원 방화벽이 목적지별로 다르게 막는지는 알 수 없습니다. 더 확실하려면 포트를 더 많이(25 · 53 · 8080 · 8443 등) 시험하고, 다른 목적지에서도 같은지 봅니다.
- (다-2) 연결에 대한 응답인 `[SYN, ACK]` · `[RST]` 와 데이터 패킷이 사라지고, 연결을 시작한 `[SYN]` 줄만 남습니다. 한 PC 가 여러 포트로 **연결을 시작한 것**만 모아 봐야 한 출발지가 몇 개의 포트로 연결을 시도했는지 바로 셀 수 있습니다.

**왜** — 맨 아래 줄이 「모두 차단」이냐 「모두 허용」이냐가 「규칙에 없는 포트」의 결과를 정합니다. 밖에서 포트를 시험하면 그 맨 아래 줄을 짐작할 수 있습니다.

**자주 틀리는 곳** — 연결 시작 SYN 만 보는 필터로는 열림(`[SYN, ACK]`)과 거부(`[RST]`)가 안 보이는데 그 화면에서 판정하려는 경우가 많습니다. 판정은 2번 필터(포트 세 개 전체)에서 하고, 시간 초과를 「서버가 꺼졌다」로 적는 경우도 많습니다. portquiz 는 모든 포트에 응답하게 만든 사이트라, 응답이 없으면 내 쪽 어딘가의 방화벽이 막은 것입니다.

**관제에서는** — 새 서비스를 열기 전에 밖에서 같은 시험으로 포트가 열려 있는지 확인하고, 열려 있으면 안 되는 포트(DB · 관리용)가 열려 있으면 바로 보고합니다.
