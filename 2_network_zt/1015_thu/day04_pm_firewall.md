### 5.1 규칙 한 줄 · 위에서부터 첫 번째로 맞는 규칙

**여기 나오는 말**

- **방화벽 (firewall)** (파이어월)
  - 망과 망 사이에서 요청마다 **허용할지 차단할지** 규칙으로 정하는 장비 · 프로그램
- **방화벽 규칙 (rule)** (룰)
  - 「어디서(출발지) · 어디로(목적지) · 어느 포트로 가는 요청을 · 허용 / 차단한다」를 적은 **한 줄**
  - 실제 장비에는 프로토콜(TCP · UDP)도 적는다. 오늘은 모두 TCP 라 생략한다
- **첫 번째 일치 (first match)** (퍼스트 매치)
  - 규칙표를 **위에서부터** 읽다가 **처음 맞는 규칙** 하나로 결정하고, 그 아래는 보지 않는 방식
- **`0.0.0.0/0`**
  - **모든 주소**를 뜻하는 망. 10/13 기본 경로와 같은 표기다
- **`any`** (애니)
  - **모든 포트**

**규칙표 R** (오늘 5교시에 읽는 규칙표)

| 번호 | 출발지 | 목적지 | 포트 | 동작 | 뜻 |

| 2 | `10.8.0.0/24` | `10.10.20.6/32` | `443` | 허용 | VPN 직원 → 웹메일 |

### 5.2 막힌 연결은 패킷으로 어떻게 보이나

10/12 에 Wireshark 로 **성공한** 연결의 3-way handshake(SYN → SYN/ACK → ACK)를 봤습니다. 방화벽이 연결을 막으면 이 인사가 중간에서 끊깁니다. 막는 방식은 두 가지입니다.

| 막는 방식 | 방화벽이 하는 일 | Wireshark 에 보이는 것 | 내 PC 쪽 결과 |
|---|---|---|---|
| **드롭 (drop)** (드롭 · 버림) | 받은 SYN 을 **조용히 버린다** | 내 PC 의 SYN 만 몇 초 간격으로 다시 나가고 답이 없다 — `[TCP Retransmission]`(재전송) 표시 | 기다리다가 시간 초과 |
| **거부 (reject)** (리젝트) | 「연결 안 받는다」고 **RST 를 보낸다** | SYN 바로 뒤에 상대의 RST | 곧바로 실패 |

- **재전송 (retransmission)** (리트랜스미션) — 답이 없어서 같은 패킷을 다시 보내는 것
- 서버 프로그램이 꺼진 포트(닫힌 포트)도 보통 RST 로 답합니다(10/12). 그래서 **RST 만으로는 방화벽 때문인지 닫힌 포트 때문인지 바로 구분되지 않고**, 답이 아예 없으면 중간의 방화벽이 버렸을 가능성이 큽니다.

방화벽 로그의 「차단」 한 줄은 패킷으로 보면 이런 모습입니다.

```
방화벽 로그   14:05:03  차단  10.8.0.21:51710  →  10.10.20.9:22   규칙 5
내 PC 패킷    SYN → (응답 없음) → SYN 재전송 → (응답 없음) → …
```

### ✍️ 문제 5-2 · 허용된 연결과 막힌 연결을 Wireshark 로 비교하기

**할 일** — Wireshark 를 켠 채 허용되는 연결(`example.com` 의 80번)과 막히는 연결(옆자리 PC 의 8000번)을 하나씩 시도하고, 두 연결의 handshake 가 어떻게 다른지 보고서에 적습니다.

**왜 중요한가** — 방화벽이 실제로 연결을 막을 때 패킷이 어떻게 보이는지 직접 봅니다. 「접속이 안 된다」는 문의가 오면 관제는 패킷으로 응답이 없는지(드롭) · RST 가 왔는지(거부)를 보고, 방화벽 문제인지 서버 문제인지 범위를 좁힙니다.

**이 문제에 나오는 말**

- **`tcp.flags.syn == 1`**
  - Wireshark 화면 필터. **SYN 이 켜진 패킷**(연결을 시작하는 SYN 과 그 답 SYN/ACK)만 보여 준다
- **`curl -m 5`**
  - `-m 5` 는 **5초까지만** 기다리고 끝내라는 옵션

**순서**

1. **[보고서]** 옆자리 사람에게 IPv4 주소를 묻고 적어 둡니다. 옆자리 사람은 `ipconfig` 의 `IPv4 주소` 를 알려 줍니다(10/13 오전 3-1 과 같습니다).
2. **[Wireshark]** Wireshark 를 열고 인터넷에 연결된 어댑터(10/12 에 캡처한 것, 보통 `이더넷`)를 더블클릭해 캡처를 시작합니다. 위쪽 필터 칸에 아래를 입력하고 Enter 를 누릅니다.
   ```
   tcp.flags.syn == 1
   ```
3. **[터미널]** 허용되는 연결을 시도합니다. 화면에 HTML 글자가 나오면 연결된 것입니다.
   ```bash
   curl -m 5 http://example.com
   ```
4. **[Wireshark]** 방금 나온 SYN 과 SYN/ACK 두 줄을 찾습니다. `Info` 칸에 `[SYN]` · `[SYN, ACK]` 가 보이고, 목적지 포트는 `80` 입니다.
5. **[터미널]** 막히는 연결을 시도합니다. `옆자리IP` 자리에 1번에서 적은 주소를 넣습니다. 옆자리 PC 의 Windows 방화벽은 밖에서 들어오는 연결을 기본으로 막습니다.
   ```bash
   curl -m 5 http://옆자리IP:8000
   ```
   5초 뒤 `curl: (28) … timed out` 처럼 끝나거나, 곧바로 `Failed to connect` 로 끝납니다.
6. **[Wireshark]** 목적지 포트 `8000` 인 줄을 찾습니다. 같은 SYN 이 몇 번 나갔는지, 그 줄에 `[TCP Retransmission]` 이 붙었는지, 상대에게서 SYN/ACK 나 RST 가 왔는지 봅니다.

   - (나) 🔍 옆자리 PC 쪽 연결은 3-way handshake 의 어디에서 멈췄나요? 그 모습은 5.2 의 두 방식 가운데 어느 쪽인가요?
   - (다) 아래 방화벽 로그의 14:05 네 줄은 `10.8.0.21` 의 PC 에서 패킷으로 보면 어떤 모습일까요? 이것이 무엇을 하려던 기록으로 보이는지도 적어 주세요.

### 왜 필요한가

1. 규칙표를 만드는 방식은 둘입니다. **허용할 것만 적고 나머지를 막거나**, **막을 것만 적고 나머지를 허용**합니다. 어느 쪽이냐에 따라 「적지 않은 것」이 열리기도 하고 닫히기도 합니다.
2. 첫 번째 일치 방식이라 **같은 규칙도 순서가 바뀌면 결과가 달라집니다.** 「허용 규칙을 넣었는데 왜 막히지?」의 대부분이 순서 문제입니다.
3. 오늘부터 판정을 코드로 합니다. 7교시에 내가 쓴 규칙표를 이 코드로 채점합니다.

### 6.1 허용 목록과 차단 목록

**여기 나오는 말**

- **허용 목록 (whitelist · allowlist)** (화이트리스트 · 얼라우리스트)
  - **허용할 통신만** 규칙으로 적고, 맨 아래에서 나머지를 **모두 차단**하는 방식
- **차단 목록 (blacklist · denylist)** (블랙리스트 · 디나이리스트)
  - **막을 통신만** 규칙으로 적고, 맨 아래에서 나머지를 **모두 허용**하는 방식
- **최소 권한 (least privilege)** (리스트 프리빌리지)
  - 업무에 **꼭 필요한 접근만** 주는 원칙. 방화벽에서는 허용 목록이 이 원칙을 따른다

| | 허용 목록 | 차단 목록 |
|---|---|---|
| 규칙에 적는 것 | 허용할 통신 | 막을 통신 |
| 맨 아래 줄 | 모두 **차단** | 모두 **허용** |
| 규칙에 없는 새 서버 · 새 포트 | 막힌다 | **열린다** |

#### 🐍 문법 상자 · `for` 안의 `for` — 요청마다 규칙을 처음부터 · `found` 를 다시 `False` 로

`found = False` 는 10/13 오후 6-2 에서 썼습니다. 오늘은 요청이 여러 개라 **요청마다** 규칙표를 처음부터 다시 읽어야 해서, `found` 를 바깥 `for` 안에서 다시 `False` 로 만듭니다.

```python
RULES = [(1, "A"), (2, "B"), (3, "A")]   # (번호, 맞는 글자) 튜플 세 개로 된 연습용 규칙표를 RULES 에 담는다
for req in ["A", "B"]:                     # 바깥 반복: 요청 글자를 하나씩 req 에 담아 반복한다
    found = False                          # 요청마다 「아직 못 찾음」으로 다시 시작한다
    for no, letter in RULES:               # 안쪽 반복: 규칙을 위에서부터 하나씩 꺼낸다
        if found == False:                 # 아직 못 찾았을 때만 아래를 확인한다
            if letter == req:              # 규칙의 글자가 요청과 같으면 아래 두 줄을 실행한다
                print(req, "→ 규칙", no)   # 요청과 처음 맞은 규칙 번호를 출력한다
                found = True               # 찾았으므로 이 요청에서는 아래 규칙을 더 보지 않는다

# A → 규칙 1     ← 3번도 "A" 지만 이미 1번에서 찾아 출력하지 않는다
# B → 규칙 2
```

| 쓰는 것 | 뜻 |
|---|---|
| 바깥 `for` 안의 `found = False` | 요청이 바뀔 때마다 「못 찾음」으로 되돌린다. 바깥 `for` 위에 두면 둘째 요청부터는 아무 규칙도 확인하지 않는다 |
| `if found == False:` | 첫 번째로 맞는 규칙 하나만 쓰고, 그 뒤 규칙은 건너뛴다 — 첫 번째 일치 |
| `rport == "any" or rport == port` | 규칙의 포트가 「모든 포트」이거나 요청의 포트와 같으면 `True` |

### 6.2 규칙 순서 — 넓은 규칙과 좁은 규칙

- **넓은 규칙** — 많은 주소 · 포트에 맞는 규칙. 예: 목적지 `10.10.0.0/16` · 포트 `any`
- **좁은 규칙** — 적은 주소 · 포트에만 맞는 규칙. 예: 목적지 `10.10.20.5/32` · 포트 `443`

넓은 규칙이 좁은 규칙보다 **위에** 있으면, 좁은 규칙에 맞을 요청이 넓은 규칙에 먼저 맞아 좁은 규칙까지 내려가지 못합니다.

**할 일** — 업무 포털 · 웹메일을 허용하는 규칙이 있는데도 VPN 직원이 막히는 규칙표를 실행해 원인을 찾고, 순서를 고친 두 번째 파일 `day04_6-2_order_fixed.py` 로 다시 실행해 보고서에 적습니다.

**할 일** — 아래 요구사항 다섯 개를 지키는 규칙표를 `RULES` 에 직접 쓰고, 시험 요청 8개로 채점해 `점수: 8 / 8` 이 나올 때까지 고칩니다.

   ```python
   for src, dst, port, expect in TESTS:                                # 시험을 하나씩 꺼내 출발지 · 목적지 · 포트 · 기대 결과에 나눠 담아 반복한다
       result = "맞는 규칙 없음"                                        # 맞는 규칙이 하나도 없을 때의 결과로 시작한다
       found = False                                                   # 시험마다 「아직 맞는 규칙을 못 찾음」으로 다시 시작한다
       for no, rsrc, rdst, rport, action in RULES:                     # 규칙을 위에서부터 하나씩 꺼낸다
           if found == False:                                          # 아직 못 찾았을 때만 아래를 확인한다
               src_ok = ipaddress.ip_address(src) in ipaddress.ip_network(rsrc)   # 출발지가 규칙의 출발지 망에 들어 있으면 True
               dst_ok = ipaddress.ip_address(dst) in ipaddress.ip_network(rdst)   # 목적지가 규칙의 목적지 망에 들어 있으면 True
               port_ok = rport == "any" or rport == port               # 규칙의 포트가 "any" 이거나 요청의 포트와 같으면 True
               if src_ok and dst_ok and port_ok:                       # 세 가지가 모두 맞으면 첫 번째로 맞은 규칙이다
                   result = action                                     # 그 규칙의 동작을 결과로 담는다
                   found = True                                        # 찾았으므로 아래 규칙은 더 보지 않는다
       if result == expect:                                            # 결과가 기대와 같으면 아래 두 줄을 실행한다
           score = score + 1                                           # 맞힌 수를 1 늘린다
           print("맞음  ", src, "→", dst, port, ":", result)            # 맞은 시험을 출력한다
       else:                                                           # 결과가 기대와 다르면 아래 줄을 실행한다
           print("틀림  ", src, "→", dst, port, ":", result, "/ 기대:", expect)  # 틀린 시험과 기대 결과를 함께 출력한다
   print("점수:", score, "/", len(TESTS))                              # 맞힌 수와 전체 시험 수를 출력한다
   ```

- (가-2) 옆자리 PC 의 Windows 방화벽이 드롭하면 SYN 이 두세 번 나가고, 두 번째부터 `[TCP Retransmission]` 이 붙으며, 상대에게서는 아무것도 오지 않습니다. `curl` 은 5초 뒤 `curl: (28) Connection timed out …` 으로 끝납니다. 학원 PC 설정에 따라 RST 가 바로 오고 `Failed to connect` 로 끝날 수도 있습니다(확인 필요) — 그때는 「거부」 방식입니다.
- (나) 첫 단계 SYN 에서 멈췄습니다. SYN/ACK 가 오지 않아 handshake 의 둘째 단계로 가지 못했고, 응답 없이 재전송만 반복됐으므로 **드롭** 방식입니다(RST 가 왔다면 거부 방식).
- (다) `10.8.0.21` 의 PC 에서는 1초 간격으로 서로 다른 서버 · 포트(관리 서버 SSH · 관리 화면, 고객 DB, 새 DB)로 SYN 을 보내고 하나도 SYN/ACK 를 받지 못한 모습입니다. 업무 포털 접속 직후에 관리용 · DB 포트를 차례로 두드린 것이라, 열린 곳을 찾는 내부 포트 스캔으로 보입니다. 오전 3.2 에서 본 VPN 게이트웨이의 기록으로 그 시각에 이 VPN 주소를 받은 사용자를 찾아 확인합니다.

**왜** — 방화벽이 버리면 SYN/ACK 가 오지 않아 handshake 가 첫 단계에서 멈추고, 내 PC 는 같은 SYN 을 다시 보내다가 시간 초과로 끝납니다.

**자주 틀리는 곳** — 시간 초과를 「인터넷이 끊겼다」로 적는 경우가 많습니다. 같은 시각에 `example.com` 은 연결됐으므로 내 인터넷은 정상이고, 그 목적지 · 포트만 막힌 것입니다.

**관제에서는** — 「접속이 안 된다」 문의에서 SYN 이 나가는데 답이 없으면 중간 방화벽 규칙부터, RST 가 오면 서버의 포트 · 프로그램 상태부터 확인합니다.
