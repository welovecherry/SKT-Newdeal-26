### 2.2 이슈 3유형과 가르는 기준

| 유형 | 뜻 | 예 | 먼저 볼 기록 |
|---|---|---|---|
| 장애 | 정상 요청이 안 되거나 느림 (연결 장애 · 성능 저하 · 서비스 장애) | 특정 사이트만 안 열림, 응답이 느림 | `ping` · `tracert` · `nslookup`, 서버 상태 |
| 위협 | 악의적인 시도 (무차별 대입, DNS 스푸핑, SYN Flood) | 한 IP 에서 로그인 실패가 계속 남 | 인증 로그, 방화벽 로그, DNS 응답 IP |
| 접근통제 | 권한 · 정책의 문제 (과다권한, 최소권한 위반, 정책 우회) | 영업팀 계정이 정산 내역을 조회함 | 정책 로그, 앱 접근 기록, 등록 정보 |

- **무차별 대입**(brute force · 브루트 포스)
  - 비밀번호를 계속 바꿔 가며 로그인을 시도하는 공격
  - 10/15(목)에 한 IP 의 로그인 실패 기록으로 찾아봤다
- **DNS 스푸핑**(DNS spoofing · 디엔에스 스푸핑)
  - 가짜 DNS 응답으로 이름을 엉뚱한 IP 에 연결하는 공격
  - 사용자는 사이트가 열리는 것처럼 보인다
- **SYN Flood**(신 플러드)
  - 연결 요청(SYN)을 한꺼번에 마구 보내 서버가 새 연결을 받지 못하게 만드는 공격
  - 10/12(월)에 배운 handshake 의 첫 단계를 악용한다
- 한 증상이 두 유형에 걸칠 수 있습니다. 증상만으로 정하지 말고 **기록으로 가릅니다.**

### 2.3 닫힘 기본 값 — 판단 서버가 응답하지 않을 때

6일 차에 PDP(판단)와 PEP(집행)를 나눴습니다. 그런데 PEP 가 PDP 에 물었는데 **답이 오지 않으면** 어떻게 해야 할까요?

- **닫힘 기본 값**(fail-closed · 페일 클로즈드)
  - 판단 서버가 응답하지 않으면 요청을 **막는** 설정
- **열림 기본 값**(fail-open · 페일 오픈)
  - 판단 서버가 응답하지 않으면 요청을 **통과시키는** 설정
- **거절과 통신 실패는 다릅니다.** 거절은 PDP 가 「거부」라고 **답한** 것이고, 통신 실패는 PDP 가 **답을 못 한** 것입니다. 중요한 자원은 두 경우 모두 막아야 합니다.
- 닫으면 판단 서버 장애가 곧 업무 중단이 되고, 열면 장애 동안 검사 없이 통과합니다. 그래서 **자원마다 다르게** 정합니다. 최소권한에서 자원마다 기준이 달랐던 것과 같은 생각입니다.

**이 시간에 나오는 말** (이미 배운 방법입니다)

- `try:` 아래 코드에서 오류가 나면 `except 오류이름:` 아래 코드로 넘어간다(9/28(월)).
- `TimeoutError` 는 응답이 제때 오지 않을 때 나는 오류의 이름입니다. `except ValueError:` 와 같은 모양으로 씁니다.

### ✍️ 문제 2-2 · 판단 서버가 응답하지 않을 때의 집행 함수 만들기

PDP 가 응답하지 않을 때의 자원별 비용

| 자원 | 닫으면 | 열면 |
|---|---|---|
| ① 정산 내역 조회 | 직원이 정산 내역을 보지 못해 업무가 멈춘다 | 검사 없이 정산 내역이 나간다 |

```python
KNOWN_DEVICES = {"junho": "NB-0522", "seoyeon": "NB-0417"}   # 계정 → 등록 기기

def decide(req):                                             # PDP: 요청 하나를 받아 (결정, 이유 목록)을 리턴한다 (6일 차 판단 함수를 줄인 것)
    if KNOWN_DEVICES.get(req["user"]) != req["device"]:      # 등록된 기기가 아니면

    if req["country"] != "KR":                               # 국내가 아닌 곳에서 접속했으면
        return "추가확인", ["해외에서 접속"]                   # 추가 확인을 요구한다
    return "허용", []                                         # 그 밖에는 허용한다

def ask_pdp(req, down):                                      # PEP 가 PDP 에 결정을 묻는 함수
    if down:                                                 # down 이 True 이면 PDP 가 응답하지 않는 상황이다
        raise TimeoutError("PDP 응답 없음")                   # 응답이 없을 때 나는 오류를 일으킨다
    return decide(req)                                       # 정상이면 PDP 의 결정을 리턴한다

def enforce(req, down, fail_open):                           # PEP: 결정을 받아 통과 · 차단 · 추가확인을 정하는 함수
    """PDP 의 결정을 집행해 (집행 결과, 이유 목록)을 리턴한다. fail_open 이 True 이면 응답이 없을 때 열어 둔다"""
    decision, reasons = "허용", []                           # 기본 결정. PDP 가 응답하지 않으면 이 값이 그대로 남는다
    try:                                                     # PDP 에 묻는다
        decision, reasons = ask_pdp(req, down)               # 결정과 이유 목록을 받는다
    except TimeoutError:                                     # PDP 가 응답하지 않으면
        pass                                                 # 임시 값: 아무것도 하지 않는다. 이 줄을 아래 다섯 줄로 바꾼다 (5줄)   # ←
        # 1. fail_open 이 True 이면 decision 을 "허용", reasons 를 ["PDP 응답 없음 — 열어 둠"] 으로 정한다
        # 2. 그렇지 않으면 decision 을 "거부", reasons 를 ["PDP 응답 없음"] 으로 정한다
        # 3. 어느 쪽이든 "[경고] PDP 응답 없음" 을 출력한다
    if decision == "거부":                                    # 결정이 거부이면
        return "차단", reasons                                # 차단한다
    if decision == "추가확인":                                # 결정이 추가확인이면
        return "추가확인", reasons                            # 추가 확인을 요구한다
    return "통과", reasons                                    # 그 밖에는 통과시킨다

REQ_OK = {"user": "junho", "device": "NB-0522", "country": "KR"}     # 정상 요청(등록 기기, 국내)
REQ_BAD = {"user": "seoyeon", "device": "NB-7741", "country": "KR"}  # 위험 요청(등록되지 않은 기기)
print("A 정상 요청, PDP 정상", enforce(REQ_OK, False, False))                         # A: PDP 가 정상이고 정상 요청
print("B 위험 요청, PDP 정상", enforce(REQ_BAD, False, False))                        # B: PDP 가 정상이고 위험 요청
print("C 정상 요청, PDP 응답 없음, 정산 조회(닫힘)", enforce(REQ_OK, True, False))     # C: PDP 가 응답하지 않고 정산 조회
print("D 정상 요청, PDP 응답 없음, 공지 페이지(열림)", enforce(REQ_OK, True, True))    # D: PDP 가 응답하지 않고 공지 페이지
```

### 3.1 JSON 줄 로그와 상관 분석

- **JSON 줄**(JSON Lines · 제이슨 라인즈)
  - 한 줄이 JSON 하나인 로그 형식
  - 줄 하나를 `json.loads(글자)` 로 딕셔너리로 바꿔서 읽는다(9/28(월))
- **상관 분석**(correlation analysis · 코릴레이션 애널리시스)
  - 여러 줄의 사건을 이어서 보고 패턴을 찾는 것
  - 오늘은 「같은 계정이 거부된 뒤 10분 안에 허용되는 것」을 찾는다
- 이 패턴은 의심 후보일 뿐 확정이 아닙니다. MFA 를 한 뒤 다시 시도해 허용되는 정상 재시도도 같은 모양입니다. **거부 이유와 기기가 바뀌었는지**로 가릅니다.

계정마다 **마지막 결정과 그 시각(분)**을 딕셔너리에 기억해 두고, 새 줄을 읽을 때마다 비교합니다. 시각 `"09:10"` 은 `to_min` 함수로 분(550)으로 바꿔 뺄셈합니다(`.split(":")` 은 10/13(화)에 배웠습니다).

로그 두 줄을 따라가면 이렇습니다.

| 읽는 줄 | `last` 에 기억된 값 | 판정 |
|---|---|---|
| `02:10 seoyeon 거부` | (없음) | 처음 보는 계정 → 기억만 한다: `last["seoyeon"] = ("거부", 130)` |
| `02:13 seoyeon 허용` | `("거부", 130)` | 마지막이 거부이고 지금은 허용이고 `193 - 130 = 3` 분 → **거부 후 허용** |

### 정답 2-1

**결과**

- (가) 한 예입니다.

| 번호 | 유형 | 먼저 볼 기록 |
|---|---|---|
| ① | 장애(또는 위협) | `nslookup shop.example` 의 응답 IP 와 방화벽 규칙 |
| ② | 위협(무차별 대입) | 인증 로그 |
| ③ | 장애(성능 저하) | `ping` · `tracert`, 서버 부하 |
| ④ | 접근통제 | 정책 로그, 등록 정보(영업팀의 맡은 자원) |
| ⑤ | 위협(DNS 스푸핑 의심) | DNS 응답 IP 와 레코드 · 캐시 |
| ⑥ | 위협(SYN Flood) | 방화벽 로그, 연결 상태 |
| ⑦ | 접근통제(퇴사 계정 회수 누락) | 계정 상태, VPN 접속 로그 |
| ⑧ | 접근통제(집행 누락) | 정책 로그와 앱 접근 기록 대조 |

- (나) ① 은 **장애**일 수 있습니다. DNS 가 그 이름만 잘못 답하거나 방화벽 규칙이 그 사이트를 막고 있을 수 있습니다. **위협**일 수도 있습니다. 가짜 DNS 응답(DNS 스푸핑)이 그 이름만 엉뚱한 IP 로 보내고 있을 수 있습니다. 확정하려면 `nslookup` 의 응답 IP 가 평소 IP 와 같은지, 방화벽 로그에 그 사이트로 가는 차단 기록이 있는지, DNS 서버의 응답 기록이 필요합니다.
- (다) ⑦ 은 **먼저 접근통제로 대응**합니다. 퇴사 계정이 살아 있는 것이 원인이라 계정을 비활성화하고 세션을 끊는 것이 먼저입니다. 동시에 그 로그인이 본인 의사가 아니라 비밀번호를 가진 다른 사람의 시도였는지(위협)는 VPN 접속 기록의 출발 IP · 시각으로 확인합니다. 접근을 막는 것이 확인보다 빠르고 피해를 줄입니다.
- (한 줄) 예: 「증상 8개를 장애 2건, 위협 3건, 접근통제 3건으로 나눴고, 유형이 겹치는 ①과 ⑦은 기록으로 가른 뒤 대응하겠습니다.」

**왜** — 증상만으로 유형을 단정하면 틀립니다. 같은 증상도 장애일 수도 위협일 수도 있어서 먼저 볼 기록으로 가르는 것이 관제의 순서입니다.
