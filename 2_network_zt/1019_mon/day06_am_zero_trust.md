> - 이 교시에서 하는 일: 접근 기록에서 의심스러운 줄을 찾고, 5대 원칙의 어느 칸이 비어 있었는지 설명하고, 기록만으로 말할 수 있는 것과 없는 것을 구분합니다.

### 왜 필요한가

1. 지난주에 본 방화벽 · VPN 은 접속이 시작되는 곳에서 확인하는 방식이었습니다. 통과한 뒤에 그 계정이 무엇을 하는지는 따로 보지 않습니다.
2. 로그인이 성공한 요청 안에도 정상과 이상이 섞여 있습니다. 어느 칸을 확인했어야 했는지 알아야 규칙으로 쓸 수 있습니다(3교시).
3. 기록에 적힌 값(사실)과 그 값으로 짐작한 이유(추정)를 구분해야 고객에게 과장 없이 보고할 수 있습니다.

### 2.1 경계 기반 보안과 Zero Trust

- **경계 기반 보안**(perimeter-based security · 페리미터 베이스드 시큐리티)
  - 회사 네트워크 안은 신뢰하고 밖은 의심하는 방식
  - 방화벽 · VPN 이라는 경계를 통과하면 내부 자원에 넓게 접근할 수 있다
- **Zero Trust**(제로 트러스트)
  - 「누구도 기본적으로 신뢰하지 않고, 접근할 때마다 확인한다」는 보안 원칙
  - 미국 **NIST**(National Institute of Standards and Technology · 닛스트, 국립표준기술연구소)의 문서 SP 800-207 이 그 구조를 정리했다
- **자원**(resource · 리소스)
  - 보호할 대상
  - 같은 포털 안에서도 정산 내역 조회와 계정 권한 변경은 서로 다른 자원이다
- **횡이동**(lateral movement · 래터럴 무브먼트)
  - 침입한 뒤 내부에서 다른 서버로 옮겨 가며 범위를 넓히는 것
  - 경계 기반 보안에서는 내부 이동을 막기 어렵다

두 방식은 세 가지 기준으로 비교합니다.

| 기준 | 경계 기반 보안 | Zero Trust |
|---|---|---|
| 신뢰 전제 | 경계 안으로 들어오면 신뢰한다 | 안팎 구분 없이 기본적으로 신뢰하지 않는다 |
| 검증 시점 | 로그인(경계 통과) 때 한 번 | 접근할 때마다, 세션 중에도 반복 |
| 접근 범위 | 인증되면 내부에 넓게 | 업무에 필요한 자원에만 최소한으로 |

- Zero Trust 가 막지 못하는 것도 있습니다. 정상 계정 · 정상 기기 · 평소 시간에 자기 업무 시스템에서 자료 수만 건을 내려받는 것처럼 **접근 자체는 정당하고 행동이 이상한 경우**는 접근을 허용할지 정하는 방식만으로는 보이지 않습니다. 사용 기록을 계속 분석하는 방법(4과목 이상탐지)이 따로 필요합니다.

**현실에서 마주치는 곳**

- **Cloudflare Access**: 사내 앱마다 따로 접근 정책을 걸고, 접속할 때마다 사용자 신원과 기기 상태를 확인합니다.
- **Microsoft Entra 조건부 액세스**(Conditional Access): 회사 기기가 보안 기준을 지킨 기기(compliant)로 표시된 경우에만 접속을 허용하는 정책을 만들 수 있습니다.

### 2.2 5대 원칙 — 요청 하나를 다섯 칸으로 읽기

Zero Trust 는 제품 하나가 아니라 **확인할 항목의 묶음**입니다. 요청 하나를 다섯 칸으로 나누면 어느 칸이 비었는지 보입니다.

- **ID**(identity · 아이덴티티)
  - 이 사용자가 진짜 본인인지 확인하는 칸
- **MFA**(multi-factor authentication · 엠에프에이, 다중 인증)
  - 비밀번호 말고 한 가지를 더 확인하는 것
  - 예: 휴대폰 승인
- **Device**(디바이스)
  - 접속하는 기기가 회사 보안 기준을 지키는지 확인하는 칸
  - 확인하는 것: 등록된 기기인지, 백신 · 패치 상태가 괜찮은지
- **Network**(네트워크)
  - 요청이 필요한 자원에만 닿는지 확인하는 칸
- **마이크로 세그멘테이션**(micro-segmentation · 마이크로 세그멘테이션)
  - 네트워크를 아주 작은 구역으로 나누는 것
  - 구역 사이 통신을 규칙으로 제한하는 것
- **Application**(애플리케이션)
  - 이 앱의 이 기능을 쓸 권한이 있는지 확인하는 칸
- **Policy**(폴리시)
  - 시간 · 위치 · 위험도에 따라 정책이 달라지는 칸
  - 예: 새벽 로그인이나 해외 IP 면 추가 인증

| 칸 | 묻는 것 | 확인하는 예 | 대표 제품 |
|---|---|---|---|
| ID | 이 사용자가 진짜 본인인가 | 비밀번호 + MFA | Microsoft Entra ID |
| Device | 기기가 회사 기준을 지키나 | 등록 기기 · 백신 · 패치 · 디스크 암호화 | Microsoft Intune(기기 준수 정책) |
| Network | 필요한 자원에만 닿나 | 구역을 나누고 구역 사이 통신 제한 | 방화벽 구역 규칙(10/16(금)) |
| Application | 이 앱의 권한이 있나 | 앱마다 따로 접근 정책 | Cloudflare Access |
| Policy | 상황에 따라 정책이 바뀌나 | 해외 IP · 새벽 로그인이면 추가 인증 | Microsoft Entra 조건부 액세스 |

- 문서마다 칸의 이름과 개수가 조금씩 다를 수 있습니다. 이 과정에서는 위 다섯 가지로 설명합니다.
- 요청 하나가 한 칸을 통과해도 다른 칸에서 걸릴 수 있습니다. 어느 칸에서 걸렸는지가 고칠 곳을 알려 줍니다.

A사 재무팀 junho 의 정상적인 정산 조회 한 건을 다섯 칸으로 읽으면 이렇습니다.

| 칸 | 이 요청에서 확인한 것 | 결과 |
|---|---|---|
| ID | 계정 `junho`, 로그인 방식 비밀번호 + MFA | 정상 |
| Device | 기기 `NB-0522` 는 junho 의 등록 기기이고 보안 상태가 정상 | 정상 |
| Network | 사내 대역 `10.20.3.14` 에서 정산 포털로 접속 | 정상 |
| Application | junho 는 정산 내역(`SETTLE`) 담당 | 정상 |
| Policy | 낮 14시, 평소 조회량(12건) | 정상 |

### 2.3 기록으로 단정할 수 있는 것과 없는 것

- **확인된 사실**: 기록에 적힌 값. 시각 · 계정 · 기기 · 출발 IP · 건수 · 결과
- **추정**: 그 값으로 짐작한 이유. 예: 「본인이 아닐 것이다」
- **출발 IP 가 사내 대역이다**는 사내망에서 접속했다는 사실입니다. 그 기기가 회사에 등록된 기기라는 뜻은 아닙니다. 기기 등록은 별도의 기록입니다.
- **「로그인 성공」 한 줄**에는 계정 확인, 비밀번호 확인, MFA 여부가 섞여 있습니다. 무엇을 확인한 성공인지 따로 봐야 합니다.
- 기록만으로 모르는 것은 「모른다」고 쓰고, 그것을 확인하려면 어떤 자료를 봐야 하는지 함께 적습니다.

### 3.1 PDP 와 점수 판단

- **PDP**(Policy Decision Point · 폴리시 디시전 포인트, 정책 결정 지점)
  - 요청을 받아 **허용 · 추가 확인 · 거부**를 정하는 곳
  - 오늘은 파이썬 함수 하나가 이 일을 한다
- **필수 조건**
  - 하나라도 어긋나면 점수와 상관없이 바로 거부하는 조건
  - 예: 재직 중이 아닌 계정, 등록되지 않은 기기
- **위험 점수**(risk score · 리스크 스코어)
  - 이상한 신호마다 점수를 더해 합계로 판단하는 방식
  - 0점에서 시작한다
- **추가 확인**(step-up · 스텝 업)
  - 비밀번호만으로는 부족해서 한 번 더 확인하는 것
  - 허용과 거부 사이의 단계
- **최소권한**(least privilege · 리스트 프리빌리지)
  - 일에 필요한 만큼만 허용하는 원칙
  - 더 위험한 자원일수록 기준을 엄격하게 둔다

오늘 쓰는 두 가지 자원의 기준입니다. 같은 이상 신호도 자원마다 점수와 기준이 다릅니다.

| 구분 | 정산 내역 조회 | 계정 권한 변경(관리자 화면) |
|---|---|---|
| 필수 조건 | 재직 중 · 등록 기기 | 재직 중 · 등록 기기 · 역할이 `account_admin` |
| 기기 보안 상태 이상 | +40 | 3-1 에서 정한다 |
| MFA 안 함 | +20 | 3-1 에서 정한다 |
| 해외에서 접속 | +30 | 3-1 에서 정한다 |
| 새벽(6시 전) 접속 | +20 | 보지 않음 |
| 20건 이상 조회 | +30 | 보지 않음 |
| 결정 | 50점 이상 거부 · 20점 이상 추가확인 · 그 아래 허용 | 50점 이상 거부 · 10점 이상 추가확인 · 그 아래 허용 |

**이 시간에 나오는 말** (이미 배운 방법입니다)

- `ACCOUNTS.get(req["user"])`: 딕셔너리에서 키로 값을 꺼내고, 없으면 `None` 을 리턴한다(10/12(월)). `req["user"]` 처럼 대괄호로 값을 꺼내는 방법은 10/13(화)에 배웠습니다.
- `reasons.append(…)`: 리스트 끝에 값을 더한다(10/15(목)).
- `return "거부", reasons`: 값 두 개를 함께 리턴한다. 받을 때는 `decision, reasons = …`(10/16(금) 4교시).
- 함수는 `return` 을 만나면 **그 자리에서 끝납니다.** 그래서 필수 조건에서 `return` 하면 아래의 점수 계산은 실행되지 않습니다.

### 3.2 판단 함수 읽기 — `decide_settlement`

요청은 딕셔너리 한 개입니다. 키는 `user`(계정) · `device`(기기) · `health`(기기 보안 상태, `"ok"` 가 정상) · `country`(접속 국가, `"KR"` 이 국내) · `hour`(시각, 0~23) · `mfa`(MFA 여부, `True` / `False`) · `count`(조회 건수)입니다. 함수는 `(결정, 이유 목록)` 을 리턴합니다.

```python
ACCOUNTS = {                                                                      # 계정 등록 정보. 계정 이름 → 정보 딕셔너리
    "seoyeon": {"employed": True,  "device": "NB-0417", "role": "sales"},         # 재직 중, 등록 기기 NB-0417, 역할 영업
    "junho":   {"employed": True,  "device": "NB-0522", "role": "finance"},       # 재직 중, 등록 기기 NB-0522, 역할 재무
    "gaeun":   {"employed": True,  "device": "NB-0188", "role": "account_admin"}, # 재직 중, 등록 기기 NB-0188, 역할 계정 관리자
    "dami":    {"employed": False, "device": "NB-0333", "role": "sales"},         # 퇴사한 계정(employed 가 False)
}

def decide_settlement(req):                                  # 정산 내역 조회 요청 하나를 받는 함수
    """정산 내역 조회 요청을 판단해 (결정, 이유 목록)을 리턴한다"""
    account = ACCOUNTS.get(req["user"])                      # 요청의 계정을 등록 정보에서 찾는다. 없으면 None
    if account is None or not account["employed"]:           # 등록 정보에 없거나 퇴사한 계정이면 (필수 조건 1)
        return "거부", ["재직 중인 계정이 아님"]              # 점수를 보지 않고 바로 거부하고 함수를 끝낸다
    if req["device"] != account["device"]:                   # 요청 기기가 이 계정의 등록 기기와 다르면 (필수 조건 2)
        return "거부", ["이 계정에 등록된 기기가 아님"]        # 바로 거부하고 함수를 끝낸다
    score = 0                                                # 필수 조건을 통과했으니 위험 점수를 0 점에서 시작한다
    reasons = []                                             # 점수를 올린 이유를 모을 빈 목록
    if req["health"] != "ok":                                # 기기 보안 상태가 정상이 아니면
        score = score + 40                                   # 40 점을 더하고
        reasons.append("기기 보안 상태 이상 (+40)")           # 이유를 목록에 더한다
    if req["country"] != "KR":                               # 국내가 아닌 곳에서 접속했으면
        score = score + 30                                   # 30 점을 더하고
        reasons.append("해외에서 접속 (+30)")                 # 이유를 목록에 더한다
    if req["hour"] < 6:                                      # 새벽(6시 전)이면
        score = score + 20                                   # 20 점을 더하고
        reasons.append("새벽 접속 (+20)")                     # 이유를 목록에 더한다
    if req["mfa"] == False:                                  # MFA 를 하지 않았으면
        score = score + 20                                   # 20 점을 더하고
        reasons.append("MFA 안 함 (+20)")                     # 이유를 목록에 더한다
    if req["count"] >= 20:                                   # 20건 이상 조회하려 하면
        score = score + 30                                   # 30 점을 더하고
        reasons.append("대량 조회 (+30)")                     # 이유를 목록에 더한다
    if score >= 50:                                          # 합계가 50점 이상이면
        return "거부", reasons                                # 거부하고 이유 목록을 함께 리턴한다
    if score >= 20:                                          # 합계가 20점 이상이면
        return "추가확인", reasons                            # 추가 확인을 요구한다
    return "허용", reasons                                    # 그 아래면 허용한다
```

흐름을 그리면 이렇습니다.

```
요청 --> [필수 조건 검사] --어긋남--> 거부 (바로 리턴)
                 |
               통과
                 v
         [위험 점수 더하기: 기기 상태, 국가, 시각, MFA, 조회 건수]
                 v
      점수 >= 50 --> 거부
      점수 >= 20 --> 추가확인
      그 외      --> 허용
```

2교시 사건의 요청(`seoyeon`, 기기 `NB-7741`)은 **필수 조건 2 에서 바로 거부**됩니다. 등록 기기를 쓰는 요청이 점수로 어떻게 쌓이는지는 아래 한 건으로 따라가 봅니다.

### 3.3 요청 한 건 따라가기

요청: `seoyeon` · 등록 기기 `NB-0417` · 기기 상태 `ok` · 국가 `KR` · 시각 2시 · MFA 안 함 · 40건 조회

| 1 | 재직 중인 계정인가 | `employed` 가 `True` | 통과 | 0 |
| 2 | 등록 기기인가 | `NB-0417` = 등록 기기 | 통과 | 0 |

    # 2. decision 이 "거부" 이면 "[거부]", req["id"], req["user"], reasons 를 출력하고, reasons 의 이유마다 reason_counts[이유] 를 1 늘린다 (4줄: if, 출력, for, 늘리기)   # ←




    # 3. decision 이 "추가확인" 이면 "[추가확인]", req["id"], req["user"], reasons 를 출력한다 (2줄)   # ←


print("허용", counts["허용"], "건 / 추가확인", counts["추가확인"], "건 / 거부", counts["거부"], "건")   # 결정별 건수를 한 줄로 출력한다
print("거부 이유별 건수", reason_counts)                      # 거부 이유별 건수를 출력한다
```

- 채울 줄은 모두 `for` 안쪽이라 앞 공백 4칸으로 시작합니다. `if` 안쪽 줄은 8칸, 그 안의 `for` 안쪽 줄은 12칸입니다.
- 채우기 전에 실행해도 오류 없이 돌아갑니다. 건수가 모두 0 으로 나오는 것이 정상입니다.

### 4.1 PDP 와 PEP — 판단과 집행을 나누기

- **PEP**(Policy Enforcement Point · 폴리시 인포스먼트 포인트, 정책 집행 지점)
  - PDP 의 결정을 실제로 적용하는 곳
  - 요청을 통과시키거나 차단하거나 추가 확인을 요구한다
  - 예: 앱 앞의 프록시, 방화벽, API 게이트웨이
- **판단과 집행의 분리**
  - 결정하는 곳(PDP)과 막는 곳(PEP)을 나누는 것
  - 나누면 좋은 점
    - 규칙을 한 곳에서 고쳐도 여러 PEP 가 같은 규칙을 따른다
    - 결정 기록(로그)이 한 곳에 모인다
- **기본 거부**(default deny · 디폴트 디나이)
  - 허용 목록에 없는 것은 모두 거부하는 방식
  - 최소권한은 「기본적으로 아무 권한도 없음」에서 출발해 필요한 것만 목록에 더한다
  - 10/15(목) 방화벽의 기본 거부와 같은 생각이다

```
사용자 --요청--> PEP --문의(요청 정보)--> PDP (decide_settlement 함수)
                  ^                        |
                  +--- 결정 (허용 / 추가확인 / 거부) +
PEP: 허용 --> 앱 | 추가확인 --> MFA 요구 | 거부 --> 차단하고 로그에 기록
```

- 오늘 3교시의 `decide_settlement` 가 PDP 의 역할을 합니다. 요청 정보를 받아 결정을 리턴합니다.
- 화요일 오후 Docker 수업에서 nginx 가 PEP 자리를 맡고, 그 뒤의 서버가 보호 대상이 됩니다.

### 4.2 ZT 성숙도 점수 — 도입한 정도를 점수로

- **성숙도**(maturity · 머추리티)
  - 회사가 Zero Trust 를 얼마나 도입했는지의 정도
- **스코어링**(scoring · 스코어링)
  - 점검 항목을 정하고 항목마다 점수를 준다
  - 그 점수로 회사가 Zero Trust 를 도입한 정도를 나타낸다
- **위험 기반 인증**(risk-based authentication · 리스크 베이스드 오센티케이션)
  - 요청의 위험도에 따라 인증 강도를 바꾸는 방식
  - 3교시의 점수 판단(허용 · 추가확인 · 거부)이 이 방식의 한 모양이다

항목 다섯 개에 20점씩, 합계 100점 만점입니다. 점수가 높을수록 Zero Trust 를 많이 도입한 상태입니다. 항목과 점수는 연습용 가정치입니다.

| 항목 | 만점 | 계산 | 5대 원칙의 칸 |
|---|---|---|---|
| MFA 적용률 | 20 | MFA 를 쓰는 직원 수 ÷ 전체 직원 수 × 20 | ID |
| 기기 보안 점검 비율 | 20 | 점검을 통과한 기기를 쓰는 직원 수 ÷ 전체 직원 수 × 20 | Device |
| 최소권한 준수율 | 20 | 초과 권한이 없는 직원 수 ÷ 전체 직원 수 × 20 | Application |
| 마이크로 세그멘테이션 적용 여부 | 20 | 적용했으면 20, 아니면 0 | Network |
| 위험 기반 인증 적용 여부 | 20 | 적용했으면 20, 아니면 0 | Policy |

직원 12명 중 MFA 를 쓰는 사람이 6명이면 `6 ÷ 12 × 20 = 10` 점입니다. 파이썬으로는 `round(6 / 12 * 20)` 입니다.

**이 시간에 나오는 말** (이미 배운 방법입니다)

- `len(리스트)`: 리스트의 요소 수(10/15(목)).
- `round(숫자)`: 가장 가까운 정수로 만든다(10/16(금) 오후).
- `점수 = 점수 + 1` 로 하나씩 늘려 개수를 세는 방법(1과목).

F ('거부', ['MFA 안 함', '해외에서 접속'])
```

- (다) 기대 결정에서 점수의 조건을 찾으면 다음과 같습니다. 결정 기준은 50점 이상 거부, 10점 이상 추가확인입니다.
  - **기기 보안 상태 이상(D)**: 단독으로 거부여야 하므로 **50 이상**이어야 합니다.
  - **MFA 안 함(C)**: 단독으로 추가확인이어야 하므로 **10 이상 50 미만**입니다.
  - **해외에서 접속(E)**: 단독으로 추가확인이어야 하므로 **10 이상 50 미만**입니다.
  - **MFA + 해외(F)**: 둘의 합이 거부여야 하므로 **합이 50 이상**이어야 합니다.
  - 그래서 답은 하나가 아니라 범위입니다. 예: `50 / 30 / 40`, `50 / 25 / 25`, `60 / 10 / 45`. 하나만 큰 값으로 두면 F 에서 합이 모자라거나 C · E 가 거부로 바뀝니다.
- (라) 기기 보안 상태 이상은 정산 조회에서는 +40 이라 20점 이상 50점 미만, **추가확인**입니다. 권한 변경에서는 **50점 이상**으로 정해야 D 가 거부가 됩니다. 권한 변경은 계정을 통째로 바꿀 수 있는 더 위험한 자원이라 같은 신호에도 점수를 더 주고 거부 기준에 쉽게 닿게 합니다(최소권한: 위험한 자원일수록 기준을 엄격하게).

**왜** — 필수 조건은 점수와 상관없이 바로 거부하고, 점수는 여러 신호를 합쳐 판단합니다. 기대하는 결정에서 거꾸로 점수의 범위를 구하는 것이 규칙을 조정하는 방법입니다.

**자주 틀리는 곳** — MFA 블록을 `score = score + 30` 처럼 숫자를 직접 쓰면 위에서 정한 `MFA_POINTS` 를 바꿔도 결과가 변하지 않습니다. 하나씩 따로 맞추다가 서로 충돌하기도 합니다. 예를 들어 MFA 를 50 이상으로 올리면 D 가 아니라 C 가 거부가 됩니다. D 를 거부로 만들려고 49 이하로 두면 추가확인에 머뭅니다. 역할 검사를 `score` 계산 아래에 쓰면 필수 조건이 아니게 되어 B 가 거부가 아니라 점수로 판정됩니다. `if` 안쪽 줄의 들여쓰기를 4칸 더 넣지 않아 `IndentationError` 가 나는 경우도 많습니다.

**관제에서는** — 규칙은 「이 요청들은 이렇게 판정돼야 한다」는 기대 결과를 먼저 모으고 점수를 조정해 만듭니다. 같은 이상 신호라도 어떤 자원인가에 따라 대응 단계(추가 확인 · 차단)가 달라지고, 권한 변경 같은 관리 기능은 가장 엄격한 기준으로 지킵니다.

- (한 줄) 예: 「지난 한 시간의 요청 7건 중 1건 허용, 2건 추가확인, 4건 거부이며, 거부 이유는 미등록 기기 `NB-7741` 2건, 퇴사 계정 1건, 해외 새벽 접속 1건입니다.」

**자주 틀리는 곳** — `counts[decision] = counts[decision] + 1` 을 `for` 밖에 쓰면 마지막 요청 하나만 세어집니다. `reason_counts[reason] = reason_counts[reason] + 1` 처럼 `.get(reason, 0)` 없이 쓰면 처음 나온 이유에서 `KeyError` 가 납니다. `for reason in reasons:` 를 `if` 와 같은 깊이로 쓰면 허용된 요청의 이유까지 세려고 해 오류가 납니다. `if decision == "거부":` 의 `==` 를 `=` 하나로 쓰는 실수도 많습니다.
