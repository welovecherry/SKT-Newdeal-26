### 왜 필요한가

1. 지난주에 본 VPN · 방화벽은 접속이 시작되는 곳에서 확인하는 방식이었습니다. 한 번 통과한 계정이 내부에서 어디까지 가는지는 따로 보지 않았습니다.
2. 재택 · 클라우드 · SaaS 가 늘어 회사 방화벽의 안과 밖을 가르기 어려워졌습니다(10/16(금) 2교시).
3. 로그인한 계정이 내부 자원에 넓게 닿으면, 계정 하나가 뚫렸을 때 피해가 내부 전체로 번집니다.

### 2.1 경계 기반 보안과 Zero Trust

- **경계 기반 보안**(perimeter-based security · 페리미터 베이스드 시큐리티)
  - 회사 네트워크 안은 신뢰하고 밖은 의심하는 방식. 방화벽 · VPN 이라는 경계를 통과하면 내부 자원에 넓게 접근할 수 있다
- **Zero Trust**(제로 트러스트)
  - 「누구도 기본적으로 신뢰하지 않고, 접근할 때마다 확인한다」는 보안 원칙
  - 미국 **NIST**(National Institute of Standards and Technology · 닛스트, 국립표준기술연구소)의 문서 SP 800-207 이 그 구조를 정리했다
- **횡이동**(lateral movement · 래터럴 무브먼트)
  - 침입한 뒤 내부에서 다른 서버로 옮겨 가며 범위를 넓히는 것. 경계 기반 보안에서는 내부 이동을 막기 어렵다

두 방식은 세 가지 기준으로 비교합니다.

| 기준 | 경계 기반 보안 | Zero Trust |
|---|---|---|
| 신뢰 전제 | 경계 안으로 들어오면 신뢰한다 | 안팎 구분 없이 기본적으로 신뢰하지 않는다 |
| 검증 시점 | 로그인(경계 통과) 때 한 번 | 접근할 때마다, 세션 중에도 반복 |
| 접근 범위 | 인증되면 내부에 넓게 | 업무에 필요한 자원에만 최소한으로 |

- Zero Trust 가 접근마다 확인하는 것은 「누구인지 · 어떤 기기인지 · 어떤 상황인지」입니다. 세부 다섯 가지 축은 3교시에서 봅니다.

**현실에서 마주치는 곳**

- **Cloudflare Access**: 사내 앱마다 따로 접근 정책을 걸고, 접속할 때마다 사용자 신원과 기기 상태를 확인합니다.
- **Microsoft Entra 조건부 액세스**(Conditional Access): 회사 기기가 보안 기준을 지킨 기기(compliant)로 표시된 경우에만 접속을 허용하는 정책을 만들 수 있습니다.

# <mark style="display:block; background:#c8e6c9; color:#1a1a1a; padding:6px 12px; border-radius:4px">3교시 (11:00–11:50) · Zero Trust 5대 원칙</mark>

> 📨 **오늘 들어온 일**
> 고객사 보안 담당이 보낸 메시지: 「Zero Trust 를 도입하려는데 무엇부터 확인해야 하나요? 접속 요청이 어디서 걸러지는지 5가지 축으로 알려 주세요.」
> - 이 교시에서 하는 일: 접속 요청을 5대 원칙의 축으로 분류하고, 가상의 A사에서 가장 먼저 고칠 축을 고릅니다.
> - 끝나면 쓰는 것: **보고서 한 줄**(A사 대표에게 보낼 답 한 문장)

### 왜 필요한가

1. Zero Trust 는 하나의 제품이 아니라 확인할 항목의 묶음입니다. 어떤 항목이 있는지 알아야 우리 환경에서 비어 있는 곳을 찾을 수 있습니다.
2. 접속이 막혔을 때 어느 축에서 걸렸는지 알아야 원인과 고칠 곳이 보입니다.

### 3.1 5대 원칙 — 확인하는 다섯 가지 축

- **ID**(identity · 아이덴티티)
  - 이 사용자가 진짜 본인인지 확인하는 축
- **MFA**(multi-factor authentication · 엠에프에이, 다중 인증)
  - 비밀번호 말고 한 가지를 더 확인하는 것. 예: 휴대폰 승인
- **Device**(디바이스)
  - 접속하는 기기가 회사 보안 기준을 지키는지 확인하는 축. 백신 · 패치 · 디스크 암호화 같은 것
- **Network**(네트워크)
  - 요청이 필요한 자원에만 닿는지 확인하는 축
- **마이크로 세그멘테이션**(micro-segmentation · 마이크로 세그멘테이션)
  - 네트워크를 아주 작은 구역으로 나누고, 구역 사이 통신을 규칙으로 제한하는 것
- **Application**(애플리케이션)
  - 이 앱에 접근할 권한이 있는지 확인하는 축
- **Policy**(폴리시)
  - 시간 · 위치 · 위험도에 따라 정책이 달라지는 축. 예: 해외 IP 에서 로그인하면 추가 인증

| 축 | 묻는 것 | 확인하는 예 | 대표 제품 |
|---|---|---|---|
| ID | 이 사용자가 진짜 본인인가 | 비밀번호 + MFA | Microsoft Entra ID |
| Device | 기기가 회사 기준을 지키나 | 백신 · 패치 · 디스크 암호화 | Microsoft Intune(기기 준수 정책) |
| Network | 필요한 자원에만 닿나 | 구역을 나누고 구역 사이 통신 제한 | 방화벽 구역 규칙(10/16(금)) |
| Application | 이 앱의 권한이 있나 | 앱마다 따로 접근 정책 | Cloudflare Access |
| Policy | 상황에 따라 정책이 바뀌나 | 해외 IP · 새벽 로그인이면 추가 인증 | Microsoft Entra 조건부 액세스 |

- 문서마다 축의 이름과 개수가 조금씩 다를 수 있습니다. 이 과정에서는 위 다섯 가지로 설명합니다.

- (다) **4번 줄**(10:05, 첫 `HR-DB` 접속)부터입니다. Zero Trust 라면 접근마다 「마케팅팀 kim 에게 인사 DB 가 업무에 필요한가」를 확인해 `deny` 했을 것입니다.
- (한 줄) 예: 「VPN 로그인은 정상이었지만 마케팅팀 계정이 인사 DB · 재무 시스템 · 소스 저장소에 접근했고, VPN 통과 뒤 내부 접근을 넓게 허용하고 있어서 막지 못했습니다. 접근할 때마다 업무 필요 여부를 확인하는 방식으로 바꾸겠습니다.」

**왜** — VPN 인증은 「누구인가」만 확인하고, 「이 사람이 이 자원에 필요한가」는 확인하지 않습니다.

**자주 틀리는 곳** — 8줄 전체가 이상하다고 답하는 경우가 있습니다. 1 · 2 · 3 · 8번은 kim 의 정상 업무입니다. 이 기록만으로 계정이 도용됐는지 kim 본인의 일탈인지는 알 수 없습니다. 판단하려면 kim 본인에게 확인하고, VPN 로그인의 기기와 IP 를 더 봐야 합니다.

**관제에서는** — 접근 기록에서 계정의 부서와 접근한 시스템을 대조합니다. 부서와 무관한 접근은 경보 규칙으로 만들 수 있습니다(4과목 이상탐지에서 다룹니다).

### 정답 2-2

**결과**

- (가) **①②③⑤** 입니다.
  - ①: 인사 DB 가 그 사용자 업무에 필요한지 접근마다 확인합니다(접근 범위).
  - ②: 비밀번호가 맞아도 평소에 없던 해외 IP 라는 상황을 확인해 추가 인증을 요구하거나 막습니다.
  - ③: 접속하는 기기의 상태(백신 · 패치)를 확인해 기준 미달이면 막습니다.
  - ⑤: SaaS 에 직접 접속해도 계정 · 기기 · 상황을 확인합니다(경계 안팎 구분이 없습니다).
- (나) **④번**입니다. 정상 계정 · 정상 기기 · 평소 시간 · 자기 업무 시스템이라 **접근 자체는 정당**합니다. 문제는 접근 이후의 행동(수만 건 대량 내려받기)이라, 접근을 허용할지 정하는 Zero Trust 만으로는 보이지 않습니다. 사용 기록을 계속 분석해 이상 행동을 찾는 방법(4과목 이상탐지)이 필요합니다.
- (한 줄) 예: 「Zero Trust 는 접근할 때마다 확인해서 많은 사고를 막지만, 정당한 권한으로 한 이상 행동까지 막지는 못해서 사용 기록 분석을 함께 해야 합니다.」

**왜** — Zero Trust 는 「접근해도 되는가」를 매번 정하는 원칙이고, 「접근한 뒤 무엇을 하는가」는 다른 도구로 봅니다.

**자주 틀리는 곳** — 「Zero Trust 를 도입하면 ④ 도 막는다」고 답하는 경우가 있습니다. 접근이 정당하면 막을 근거가 없습니다. ②를 경계 기반 보안도 막는다고 답하는 경우도 있습니다. 비밀번호가 맞으면 VPN 은 통과시킵니다.

**관제에서는** — Zero Trust 의 접근 기록을 이상탐지로 넘겨 「정상 접근 뒤의 이상 행동」을 찾습니다.

### 정답 3-1

**결과**

- (가) ① **ID**(관리자 계정인데 MFA 없음), ② **Device**(백신 꺼짐 · 패치 미적용), ③ **Application**(인사 시스템 앱에 권한 없음), ④ **Network**(앱을 거치지 않고 서버 구역으로 직접 연결), ⑤ **Policy**(해외 IP · 새벽), ⑥ **통과**.
- (나) ⑤ 는 비밀번호와 MFA(ID), 회사 노트북(Device), 영업 앱 권한(Application) 이 모두 정상입니다. 그런데 평소 서울에서만 로그인하던 사용자가 **새벽에 해외 IP** 로 접속한 점이 평소와 다릅니다. Policy 축은 시간 · 위치 · 위험도 같은 **상황**을 보고 추가 인증을 요구하거나 막습니다.
- (다) ③ 은 **Application** 축으로, 「이 앱에 접근할 권한이 있는가」를 확인합니다(인사 시스템 앱에 마케팅팀은 권한이 없습니다). ④ 는 **Network** 축으로, 「이 요청이 필요한 자원에만 닿는가」를 확인합니다(앱을 거치지 않은 DB 직접 연결은 구역을 나눠 두면 아예 닿지 않습니다).

**왜** — 같은 「접근하면 안 되는 곳」이라도 앱 권한의 문제인지 네트워크 경로의 문제인지에 따라 고칠 곳이 다릅니다.

**자주 틀리는 곳** — ⑤ 를 ID 축이라고 답하는 경우가 많습니다. 계정과 MFA 는 정상이어서 ID 축은 통과합니다. ③ 과 ④ 를 둘 다 Network 라고 답하는 경우도 있습니다.

**관제에서는** — 막힌 요청의 기록에서 걸린 축을 먼저 확인합니다. 정상 로그인인데 걸렸다면 Policy 축(위치 · 시간)을 봅니다.

### 정답 3-2

**결과**

- (가) 한 예: **ID 축**입니다. 사고 기록에서 비밀번호가 유출된 일반 직원 계정으로 해외 IP 로그인이 **성공**했는데, A사는 관리자 계정만 MFA 를 씁니다. 일반 직원도 MFA 를 켰다면 비밀번호만으로는 로그인할 수 없었을 것입니다. 다른 축(Device · Policy 등)도 필요하지만, 실제 사고가 난 빈틈이 ID 라서 가장 먼저입니다. 사고 기록과 연결해 이유를 쓰면 다른 축을 골라도 맞습니다.

**관제에서는** — 사고 기록(로그인 성공 · 실패)이 우선순위의 근거입니다.
